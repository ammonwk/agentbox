# agentbox v2

One place to see, start and continue every coding-agent session on this
machine — Claude Code, Codex, Devin and omp — across every subscription you are
logged into, with new sessions placed on whichever account has the most room.

This file is the contract between the pieces. If a change contradicts it,
either the change is wrong or this is: say which, in the same commit.

## What changed from v1, and why

v1 ran omp only, over ACP, in detached host processes, and let other agents
spawn omp agents as MCP subagents. v2 drops the omp-only host entirely. What
it keeps from v1: the subagent MCP (see below), skills management, the
machine and per-session load metrics, worktree reclaim, repos, PR lookup, the
router and the WebSocket split between hot state, cold state and metrics.

What it takes from switchyard: reading every provider's own transcripts as the
source of truth, tmux as the only way a session is driven, and adopt
(stop a CLI session, resume it under agentbox) with its check-before-kill
ordering.

v1's board chats were omp sessions, and omp kept its own transcript of each
all along, so they came over as ordinary v2 omp sessions: 114 of v1's 129,
imported by `scripts/import-v1.ts` (commit `7825eba`, since removed) with
their worktree and archive state; the rest never started a conversation.
v1's own data — `agentbox.db`, its per-session event logs and host logs —
is in `~/agentbox-v1-archive-2026-09-24.tar.gz`, and the last v1 commit is
tagged `v1`.

## A session is the provider's, not ours

Every provider already writes a durable transcript. agentbox never writes a
second copy of the conversation; it reads theirs.

| provider | transcript | live-process signal | resume |
|---|---|---|---|
| claude | `$CLAUDE_CONFIG_DIR/projects/<slug(cwd)>/<uuid>.jsonl` | `$CLAUDE_CONFIG_DIR/sessions/<pid>.json` (`sessionId`) | `claude --resume <uuid>` from the original cwd |
| codex | `$CODEX_HOME/sessions/YYYY/MM/DD/rollout-<iso>-<uuid>.jsonl` | `codex` pid, its `CODEX_HOME` from `/proc/<pid>/environ`, cwd, rollout mtime | `codex resume <uuid>` |
| devin | `~/.local/share/devin/cli/sessions.db` + `transcripts/<id>.json` | `session_locks/` | `devin -r <id>` |
| omp | `~/.omp/agent/sessions/<slug>/<iso>_<uuid>.jsonl` | `omp` pid + file mtime | `omp -r <path>` (by id if the file cannot be found: `-r <id>` searches, and from another project stops to ask about moving the session) |

The database holds only what the provider cannot: which account a session is
pinned to, its claim on that account, whether it is Big, the tmux session it
runs in, a label, when it was closed, and the metrics we collect for calibration.
A session row is keyed by `(provider, agentSessionId)` and gets a short
agentbox id for URLs.

## Every agentbox session is a real TUI in agentbox's own tmux

`tmux -L agentbox`, one tmux *session* per agent session, named
`ab-<shortid>`. One session each (not one window each in a shared session) so
that a terminal and a browser can both be attached without switching each
other's windows.

This is what makes "start in the CLI, continue in the app, and back" a
non-event: `agentbox claude` starts the agent in tmux and attaches your
terminal; the web UI attaches a PTY to the same tmux session and renders it
with xterm.js; detaching either leaves the agent running. The structured
timeline beside it comes from the transcript, not the screen.

A session started with plain `claude` in some other terminal is still
discovered from its transcript and shown read-only. **Adopt** moves it into
agentbox: prove the resume will land (transcript exists at the slug of the
resume cwd), SIGTERM the process, wait for it to exit, `--resume` in tmux on
the same account. Never kill first.

Input from the web goes through `tmux load-buffer` + `paste-buffer` (bracketed
paste, so multi-line text stays one prompt) and a separate `Enter`. Every write
targets the tmux session by name (`=ab-<id>:`), never a stored pane id — tmux
renumbers panes when its server restarts.

An agent agentbox launches or resumes is told where it runs
(`src/core/providers/briefing.ts`), appended to its system prompt: claude and
omp by `--append-system-prompt`, codex by `-c developer_instructions`; devin
has no such flag. Today it says one thing — that an image named in Markdown,
`![what it shows](/tmp/shot.png)`, shows in the timeline, which reads the file
through `/api/sessions/:id/image`. The transcript keeps only the path. An
adopted claude session launched with an `--append-system-prompt` of its own
keeps that one instead.

## Parking idle sessions

An idle Claude process still costs 1–2% of a core and ~240 MB (measured: 82
idle ones held 1.4 cores and 19.6 GB). Once a session has been idle for
`parkIdleMin` (60; 0 turns it off) its prompt cache is cold anyway, so the
fleet stops the process — "parks" it — and the next message resumes it with
that message as the prompt. A parked session keeps `status: "waiting"` (it is
still your move) with `host: "none"` and `parkedAt` set; stopping one
yourself makes it `stopped`. Claude sessions in agentbox's tmux only; never
one showing a permission prompt, never one with a
terminal or browser attached, and never before its resume is proven.

The unit is the tmux session: a lead's teammates are panes in it and are
stopped with it, so all of them must be idle. A turn that has been silent for
two hours counts as idle whatever Claude's status file says — it says "busy"
for days on a lead with teammates.

Anything that would wake the session later is a *hold*, shown on the session
as `parkHold`: a background command that will finish, a Monitor (its output is
messages to the session), a `/loop` wakeup still due, a cron job (one-shots
until they fire), in-process subagents that wrote in the last thirty minutes,
subagent-MCP agents still running (not finished ones holding an uncollected
answer), a teammate mid-turn or recently active, or CPU use above an idle
Claude's. Background processes that can never finish do not hold: bare log
followers (`tail -f`, `journalctl -f`, `watch`) and `while true` loops with no
way out, while they are between rounds; dev servers and tunnels hold for four
hours. A command that has only been sleeping between polls holds for a day
of quiet (a condition that can never come true looks the same forever); real
work holds for as long as it runs. Timers set by an earlier process of the
session died with it and hold nothing. A session is parked only after
two clean checks a minute apart with nothing written or started in between,
and teammates stopped with a lead are named to it in its next prompt. The
rules are in `src/core/park.ts`.

## Crash recovery

A crash stops every agent at once — the machine restarting, your user's
systemd being stopped (a logout, or a stray SIGTERM), agentbox's tmux server
dying — and with them every background command, monitor and subagent they
were waiting on. Recovery brings back what the crash took, and only that
(`src/core/recovery.ts`).

The fleet writes down what every running session is doing as it goes:
`$AGENTBOX_HOME/live-sessions.json`, rewritten whenever a session starts,
stops or changes state, and once a minute regardless. Per session: where it
runs, its status, what it is waiting on you for when blocked, and — with its
turn over — the work it is still waiting on, judged by the parking rules (a
background command, a monitor, a wakeup, subagents; a dev server does not
count). A session in another terminal is written down with its launch flags
and its shell's variables; a run another session started (a teammate, a
`claude -p`) is not, since it comes back with that session or not at all.

A crash is proven, never guessed from one session being gone: since the
snapshot, the machine booted, your user's systemd is a different process, or
the tmux server is. Checked when the server starts, against the previous
run's snapshot, and on every pass after. The tmux server dying alone takes
only what ran in it; a session in another terminal that is gone was closed
there. A session stopped by you or by the fleet, or parked or closed since, is
left alone. Then, per session:

- **resume** — mid-turn, or its turn over but waiting on work the crash
  killed. Resumed on its own account, warmest cache first, three seconds
  apart, with a prompt saying what happened: its background work is gone, and
  any address it held for another session is stale.
- **park** — its turn over with nothing running, or waiting on you (a
  question, a permission). `status: "waiting"`, `parkedAt` the time it was
  last seen; your next message resumes it. One that was waiting on you is
  told, in that prompt, that the dialog is gone (`parkedWhy`).
- **revive** — a subagent-MCP agent that was mid-turn or holding an
  uncollected answer comes back through its caller's resume (see Subagent MCP).
  A finished one is left.

A crash more than a day before the server notices it parks everything. The
report — each session, what was done and why — is saved in
`$AGENTBOX_HOME/recovery/<ms>.json` and logged; an executable of yours at
`$AGENTBOX_HOME/notify` is run with its summary as the one argument, to relay
it to wherever you will see it (`AGENTBOX_NOTIFY=0` turns that off). `agentbox recover`
shows what a crash now would do; `--last`, the last
recovery; `agentbox recover <id>...` recovers stopped sessions by hand, as they
were last seen running.

Every session the fleet starts or resumes is then watched for ten minutes:
two tool calls refused by a permission rule ("User skipped this tool call")
mean it came back unable to act — it reads the refusals, concludes it cannot
do its job, and stops. A devin session is stopped and resumed once with its
saved permission mode fixed (devin resumes in the mode `sessions.db` saved
and ignores `--permission-mode`; the adapter's `prepareResume` sets it before
every resume); anything else is shown `blocked` with the reason, and a
recovery's report says so.

## Sessions that start sessions

Agents start agents: a lead's teammates, a `codex exec` or `claude -p` run
from a Bash tool, a session that runs `agentbox codex --detach`. Each is a
session of its own, and a release or a babysit can leave dozens. A session's
`parent` is the session that started it; the board and `agentbox ls` list a
child under its parent, folded; once its parent is closed or gone, a child
that still runs shows at the root, and a stopped one is shown closed
(resumable by id) rather than stranded there. The fleet records it once,
from proof, never from titles or paths (`Fleet.linkParents`):

- **Claude teammates.** A member stamps `teamName` on every record; its
  lead's transcript has a `teammate_spawned` tool result naming the same
  `team_name`. (The team's `config.json` also has a `leadSessionId`, but it is
  not the lead's transcript id, so it is not used.)
- **The process tree.** A running session whose process has another
  session's process above it is that session's child — but only if its
  conversation began under that process, so a session merely resumed from
  inside another is not claimed. Provider environment variables are no help
  here: `CLAUDE_CODE_SESSION_ID` is inherited by the agentbox and tmux servers
  from whichever session last restarted them, so every pane carries a stale
  one.
- **The API.** `POST /api/sessions` takes the caller's pid (the CLI and the
  fleet MCP send theirs), and the session above it is the new one's parent.
  A detached orchestrator, whose process tree no longer reaches the session
  it works for, names the parent outright (`parent`), and `PATCH` sets or
  clears one after the fact.
- **You.** Drag a row onto another on the board to put it under that one, or
  out from under its parent to the top level (`PATCH` with `parent`). That
  parent is yours (`parentByHand`): the fleet never links the session again,
  and it is a grouping, not a run its parent made, so it is not shown closed
  when it stops. A subagent cannot be moved: it stops with the session whose
  MCP runs it.
- **Subagent-MCP agents.** Each records the session that asked for it
  (`owner` in its `meta.json`), which wins over the process tree. See
  [Subagent MCP](#subagent-mcp).

What cannot be told: a child whose parent's transcript is gone, one
that ran and stopped before agentbox saw its process, and work handed to a
detached daemon (the Codex plugin's shared app-server broker). Those show at
the root. Stop and the rest act on exactly the ids they are given; close
takes the sessions a parent started, at any depth, off the board with it —
running ones are stopped, the parent first (its death takes its MCP servers
and the pool agents they run), and the app asks first when any are running.

## Accounts

An account is a provider plus a credential home:

| provider | isolation | default account |
|---|---|---|
| claude | `CLAUDE_CONFIG_DIR=<home>` | `~/.claude` (env unset) |
| codex | `CODEX_HOME=<home>` | `~/.codex` |
| devin | `WINDSURF_API_KEY` read from `<home>/devin/credentials.toml` (login runs with `XDG_DATA_HOME=<home>`) | the default XDG dir (env unset) |
| omp | omp balances its own credential pool; one implicit account | `~/.omp` |

Each adapter owns its provider's homes and environments: `defaultHome()`,
`accountCommand()` for running a session, and `authEnv()` for the CLI's own
login and status commands (the same, except devin's XDG variables).

devin records no account per session, so its sessions are all listed under
the default account; one agentbox started on another account is matched back
to that account when it spawns.

Non-default homes live in `~/.local/share/agentbox/accounts/<id>/`. Shared
configuration is symlinked in from the default home so every account behaves
the same: for claude `settings.json CLAUDE.md skills agents commands plugins
hooks output-styles statusline* keybindings.json`, for codex `config.toml
AGENTS.md skills rules prompts hooks.json`, for devin `config.json` into
`<home>/config/devin/`. Credentials, `.claude.json`, transcripts and codex's
sqlite state are never shared. A new claude home gets its own `.claude.json`
seeded from an allowlist of preference keys in `~/.claude.json` (onboarding
done, theme, `mcpServers`, completed migrations) so it skips the first-run
screens; identity, usage cache and per-project state are never copied.

Transcripts are deliberately **not** shared between accounts. Sharing them
would let `claude --resume` pick up another account's session, which is
exactly the cache invalidation this whole feature exists to avoid.

A session is pinned to its account only while its prompt cache is warm.
Once it has been idle longer than `claimIdleMin` (60 minutes — the cache is
cold by then) it is `cold`: the board shows it on "any account", and when it
is woken — resumed, or sent a message — the balancer places it like a new
session. If that is another account, `Fleet.wake` proves the resume (cwd,
transcript), stops the process if one is idle in tmux, **moves** the
transcript into the new account's home (claude: the `.jsonl` and its sibling
directory, plus file-history, session-env, tasks and todos keyed by the
session id; devin: nothing to move, every account shares one store), records
an `assignments` row, and resumes there with the message as the prompt. A
move that fails resumes on the old account. Codex keeps sessions in sqlite
state as well as rollouts, and omp has one account, so neither moves.

A session that stopped at its account's limit (`limitHit`: the provider's
limit message is the last thing it wrote) is never moved automatically — a
warm cache would be thrown away. The UI offers "Continue on <the balancer's
pick>", which is `POST /api/sessions/:id/move` with the prompt "Usage limits
have reset, continue".

A session whose turn ended on the provider instead of finishing (`turnError`:
`{at, kind, detail}`) also stopped without meaning to. `kind` says what a
retry is worth: `output-cap` — the reply was cut off by the model's max
output tokens (devin's `finish_reason: "max_tokens"`, Claude's "response
exceeded the 32000 output token maximum") and a message continues it;
`transient` — a server or network failure (overloaded, connection dropped
mid-response) that a retry has a real chance of fixing; `fatal` — a retry
cannot fix it (context too long, the model or subscription is gone,
authentication). All three read as plain `waiting` otherwise, so the
attention reason says which, the rail shows the reason instead of the
cut-off tail, and the session view offers Continue/Retry for the retryable
kinds (a plain send). The fleet auto-nudges the retryable ones through the
same guarded path as error screens — 5 minutes quiet first, one nudge across
the fleet at a time, three per spell, only while the error is fresh — and
never a fatal one. An error that names its own wait (`retryAfterMs`) is left
that long instead and retried at that pace until it clears, with no cap on
tries: Codex's "Selected model is at capacity" (`codex_error_info:
"server_overloaded"`) is `transient` with a 10-minute wait. The next prompt
clears it. Rate limits stay on
`limitHit`, whose wait-out logic is theirs.

Never copy credentials between homes. Both Claude and Codex rotate refresh
tokens; two homes holding the same refresh token means one of them is logged
out the next time the other refreshes. Every account gets its own login.

agentbox never refreshes a token itself. Usage reads that hit an expired token
report `stale` with the last good reading; the next CLI run on that account
refreshes it.

An account's email is re-read from its credential home every minute, so a
`/login` inside a home changes who the account is. Its label follows unless
you named it yourself; logged out, it has no email.

The rows in the `accounts` table are **credential homes**; an account is a
**login**. Two homes of one provider logged in as the same email are one
account: the dedicated home (or else the older) owns it, and the other is a
twin. `owners()` in `src/core/accounts/homes.ts` is the one place that is
resolved, and everything keys on it: the account list (`AppState.accounts`)
has one entry per login, with the other homes in its `alsoAt`; a session's
`accountId` is its home's owner; the balancer, claims, the attributor and
rate-limit hits all count per account. A session stays pinned to its *home* —
that is where its transcript is and what resumes it — and moving it between
two homes of one account is never offered, since it would cost a cold start
and change nothing about the limits. No view re-derives any of this.

That makes the default home **your CLI login**, not a subscription: every
subscription gets its own home, and the default home is a twin of whichever
one the plain CLI is logged into, so re-logging the CLI never takes an account
away from agentbox. Sessions you start from the CLI stay in the default home
and belong to its owner. The default home cannot be forgotten — it is
re-registered at the next start, and CLI sessions live in it. A default home
logged into an account no dedicated home has is an account of its own, and the
Accounts page offers to give agentbox its own login for it. Two *dedicated*
homes on one login are a mistake the page flags until one is logged into
someone else or forgotten. An account with no
login (mid-login, or logged out) is never placed on.

### Login

Driven from the web UI; the CLI runs in a PTY and the URL/code it prints is
shown to you. A login is done when the CLI exits 0 *and* its credential file
is there.

- claude: `CLAUDE_CONFIG_DIR=<home> claude auth login --claudeai`; show the
  URL, accept a pasted `code#state`.
- codex: `CODEX_HOME=<home> codex login --device-auth`; show the verification
  URL and one-time code.
- devin: `XDG_DATA_HOME=<home> XDG_CONFIG_HOME=<home>/config devin auth login
  --force-manual-token-flow`; show the URL, accept the pasted token.
- omp: not from agentbox. omp pools its own credentials; run
  `omp auth-broker login <provider>` yourself. Adding, importing or logging in
  an omp account is refused with a 400.

Codex uses a fixed localhost callback port, so logins run one at a time per
provider.

### Usage

Each account publishes a list of windows:

    { id, kind: "short" | "weekly" | "daily" | "monthly", label,
      usedPct, resetsAt, windowMs, scope?: { model } }

- claude: `GET https://api.anthropic.com/api/oauth/usage` with
  `anthropic-beta: oauth-2025-04-20` (every 3 min per account, backing off on
  429), plus the free `cachedUsageUtilization` in each home's `.claude.json`
  whenever it changes. `five_hour` → short, `seven_day` → weekly,
  `limits[kind=weekly_scoped]` → weekly with a model scope.
- codex: `rate_limits` on `token_count` events in rollouts (free, as fresh as
  the last turn), plus `GET https://chatgpt.com/backend-api/wham/usage` for
  accounts with nothing running. Weekly only since August 2026, but the code
  takes whatever windows it is given.
- devin: best effort from `GetUserStatus`; absent is shown as unknown.
- omp: `omp usage --json`.

Readings are written to `usage_samples`, the raw material for calibration:
a row when a window's value or reset moves, and otherwise at most hourly.

## Placing a new session (the balancer)

`src/core/balancer.ts` is a pure function from account state to a choice, with
the full reasoning attached. Everything is in **weekly percentage points**.

Inputs per account: weekly used `W` and reset, short-window used `F` and reset
(claude), and the outstanding claims of its active sessions.

- A session **claims** weekly points when it is placed: what its model is
  expected to use (`claimFor`, `src/core/claim.ts`) — Fable 6, Astra 5, Opus
  2.4, Sol 2, Sonnet 1.6, and the small ones (Luna, Haiku, GLM-Flash) 0.8,
  times the effort level (low ½, high 1, max 2; devin bakes the level into
  the model id), times the Big ratio (`claimBig`/`claimNormal`) for a Big
  session. A model the table does not know claims `claimNormal` (3), which is
  what calibration keeps honest. Its outstanding claim is
  `max(0, claim − consumedSoFar)`, where consumption is the account's observed
  weekly increase apportioned across its active sessions by token-weighted
  cost. A claim lapses when the session has been idle `claimIdleMin` (60).
- Effective weekly `W' = W + Σ outstanding`. Effective short `F' = F + Σ
  outstanding × 100 / shortWindowInWeekly` (24: one full 5-hour window is about
  24 weekly points), because the next hour of a session lands in the current
  short window.
- **Pace**: how fast the short window is really filling, from its readings
  over the last ~45 minutes (`usage_samples`; at least 10 minutes of them).
  Claims only count what the balancer placed; the pace also sees a lead's
  teammates, a session run by hand, one bigger than its claim. So with a pace,
  `F'` is a forecast: `F + pace × hours to reset`, plus the claims the pace has
  not seen yet — each outstanding claim times the share of the pace's span
  that had passed before its session was here to spend (started, or woken onto
  the account). A session started ten minutes into a 45-minute span counts
  about ¾ of its claim; one running since before the span counts none, since
  its spending is in the pace already. Without a pace, `F'` is `F` plus every
  claim. (The wake time lives in memory: a restart counts a session woken just
  before it as measured.) The new-session dialog hatches `F'` on the 5-hour
  bar, so what it shows is this forecast. Teammates and other sessions started by another one carry no claim of their
  own: their parent's covers them, and the pace shows what they really spend.
- **Gate**: an account can take a new session while `W' < 100` (and, for a
  model with a scoped weekly limit, that scope's `W' < 100`), while it is not
  actually at its short-window limit (`F ≥ 100` with no reset within
  `resetHorizonMin`), and while its pace would not run the short window out
  more than 10 minutes before it resets: a session there stops mid-work.
- **Rank** (claude): first, whether it has room in its short window for this
  session's claim (`claim × 100 / shortWindowInWeekly`: 12.5 for a normal
  session). Room is short-window leg room `100 − F'`,
  raised toward 100 as the short window's reset approaches within
  `resetHorizonMin` (60), then capped by weekly headroom in short-window units,
  `(100 − W') × 100 / shortWindowInWeekly`. Among the accounts with room, the
  most weekly left per hour until its weekly reset wins: the weekly is a budget
  lost at the reset, the 5-hour a wall that stops sessions where they stand.
  Among those without room, the most room (the least overrun) goes first.
- **Rank** (weekly only, codex): most weekly left per hour until reset.
- **Overflow**: nothing passes the gate, but some enabled account still has
  real weekly left (`W < 100`) and is not at its short-window limit. Claims are estimates, so rather than leave
  work undone, place on the least-claimed of those (lowest `W'`, then most
  room), as `mode: "overflow"`, and say so.
- Nothing at all: every account is at its weekly or short-window limit, or
  turned off. Say so,
  and let a manual pick override.

Worked example: A is at 13% weekly with four days left but its 5-hour window
is filling at 29%/h and would run out 20 minutes before it resets; B is at 14%
weekly, four days left, 30% of its 5-hour, filling at 7%/h; C is at 49%, six
days left, 5-hour fresh. A is out (pace). B and C both have room for a normal
session, and B has 0.84 weekly points an hour to spend before its reset
against C's 0.32, so B takes it — though C has more 5-hour room.

A session that stops at its 5-hour limit carries on where it is
(`Fleet.continueStalled`): a minute after the window resets it is told to go
on, on the same account. A weekly limit is left to you. Nothing the fleet does
by itself moves a session to another account — not this, not an error nudge —
so a move is always one you chose.

A turn that dies mid-flight is the other way a session stalls: the CLI stays
up with the error on screen ("Send a message to retry") and the transcript
never closes the turn, so the board would call it working forever. A turn open
but silent for two hours reads waiting instead (`STALE_TURN_MS`, the judgment
recovery already makes); a devin session showing the retry error at the foot
of its screen reads `blocked` — rate limit, or error — and
`Fleet.nudgeErrored` tells it to go on once the error's reset window has
passed: one nudge across the fleet at a time (several sessions retaking one
rate-limited account in lockstep is what stuck them in the first place), three
per spell, then it is yours. An error that names its reset — devin's "Reached
free model rate limit … Your limit will reset in 1 hour 17 minutes" — is left
until then and nudged once it has passed, however long that is, with no cap on
tries: every retry before it is refused the same way, after a round of devin's
own retries (`statedWaitMs`, `src/core/retrywait.ts`). The wait counts from
the hit devin logged (`limitHit`) when there is one, else from when the fleet
first read that error off the screen. A nudge types where the session is,
however cold.

Every placement writes an `assignments` row holding every candidate as the
balancer saw it (weekly and short used, resets, summed outstanding claims, the
derived room and gate), the settings in force, the mode and the reason. That
is enough to see why each placement went where it did, and to replay the
ranking against other settings; it is not the raw windows or the per-session
claims, so a replay that changes how claims are apportioned needs the
`usage_samples` and `token_samples` of the same week.

### Calibration

`src/core/calibration.ts` reads the metrics tables and proposes settings:

- `shortWindowInWeekly`: regression of weekly increase on short-window
  increase over intervals where neither window reset.
- `claimNormal` / `claimBig`: the distribution (median, p75, p90) of what
  sessions actually consumed, split by the Big flag. With claims scaled by
  model (`src/core/claim.ts`), these two are the fallback for models the
  table does not know and the Big ratio, not every session's number.
- how often a placement was followed by a rate-limit hit on that account.

## Master session

`agentbox mcp` is an MCP server for one conductor session with a compact view
of the whole fleet: `fleet` (every session, plus each account's usage),
`read_session`, `send`, `spawn`, `resume`, `interrupt`, `close`. It is a
thin client of the HTTP API and needs the server running. The conductor is an
ordinary claude session started from the UI with that server attached;
nothing about it is special to the rest of the app.

## Subagent MCP

`agentbox subagent-mcp` is a separate MCP server, for any agent that wants to
delegate: `agent`, `send_message`, `collect`, `list_agents`, `transcript`,
`interrupt`, `stop_agent`, `workflow`. Each agent is an ACP process — `omp
acp` by default, `devin acp` when the caller passes `provider: "devin"` —
owned by the MCP server, run in the caller's working directory (or `cwd`) and
blocked on like a function call; `workflow` runs a script that fans many out.
For independent tasks, use one `workflow` with `parallel`: clients such as
Devin serialize separate blocking `agent` calls. Workflows default to six
concurrent agents; callers can set `concurrency` up to the total-agent bound
(200), including one slot per task when the whole batch should run together.
It needs neither the agentbox server nor the database, and its agents die with
it — but not for good. Every process agentbox starts has `AGENTBOX_SESSION`
set to its session id (and a claude has `CLAUDE_CODE_SESSION_NAME` too, so
other Claude sessions message it by that id rather than its folder's), which the MCP inherits and writes into each agent's
`meta.json` as `session`. When that session runs again, its new MCP brings
back, parked under the same names, the agents its last run left unfinished:
cut off mid-turn, or holding answers nobody collected (restored to their
mailboxes from the record). The next `send_message` resumes each one's own
conversation with its own system prompt, model and permissions, as after an
idle park; every tool result says which are back until each is spoken to or
stopped. An MCP shut down with its client records why (`CALLER_GONE`,
distinct from a caller's `stop_agent`), so a finished agent stays finished. omp runs `AGENTBOX_SUBAGENT_OMP_MODEL`, else
`opencode-go-responses/muse-spark-1.3-contributor`; devin runs
`AGENTBOX_SUBAGENT_DEVIN_MODEL`, else its own configured default.

The CLIs differ in two ways the pool hides (`src/subagents/backend.ts`). omp
takes the subagent contract as `--append-system-prompt`; devin has no such
flag, so the contract leads the first message of the conversation. A
read-only omp agent is started with `--tools` naming only tools that cannot
write (omp asks permission before a shell command but never before an edit);
a read-only devin agent is put in its `ask` mode, which has no write or shell
tools, and a devin writer in `bypass`.

It keeps its data under `$AGENTBOX_HOME`:

- `subagents/<pid>-<n>-<name>/` — one per spawn: `system.md` (the subagent
  contract it was given), `meta.json` (identity, the CLI, the brief, and the
  CLI's session id), `state.json` (a snapshot refreshed every 2s) and `transcript.jsonl`
  (the event log). Pruned after 7 days.
- `live/*.live` — one pre-rendered status line per agent that is running or
  holding an uncollected answer, and per workflow:
  `<unix s>\t<cwd>\t<owner>\t<text>`, read by a status-line script.

Each CLI keeps an agent's own transcript in its default store (omp runs
without `--session-dir`), beside every other session of that CLI. The fleet
tells a pool agent by its `meta.json` `provider` and `sessionId`
(`poolAgents` in `src/subagents/record.ts`) and shows it as a child of the
session its `owner` names, folded under it, titled with the agent's name.
While its MCP server lives, its `host` is `subagent`: read-only, because the
server holds the conversation open and would take a stop, an adopt or a typed
message for a crash, so the API refuses those and points at the parent.
Its status and `subagent.answerWaiting` (a finished turn its caller has not
collected) come from the server's `state.json`, which knows before the
transcript does. Stopping or closing the parent stops them all, and the UI
says which before it does. Once stopped, a pool agent is an ordinary stopped
session and can be resumed in agentbox's tmux; it stays listed only while its
parent's process runs, and is shown closed after that, so an old fan-out
neither lands at the root of the board nor piles up under a stopped parent. Code: `src/mcp/subagent.ts` over `src/subagents/`.

Who agentbox works for is the machine's business, not the repo's: `agentbox
onboard` (and the server's boot, when the file is missing) derives a name,
email, GitHub login and timezone from git, `gh` and the passwd entry, and
writes what it finds to `<agentbox home>/user.env`. The file wins over
derivation; re-onboarding fills only keys still missing, so a hand-written
`USER_CONTEXT` — the line the voice agent knows its human by — survives. The
voice prompt and the Deepgram keyterm bias are built from this file and the
tracked repos' names; nothing personal is hardcoded anywhere.

Setup is one checklist, computed by probes and rendered the same everywhere —
the board's first-run card, `agentbox onboard` and `doctor` all read
`onboardingItems` (`src/core/onboarding.ts`), so no two views of "what is
missing" can disagree. Its inventory: tmux and git; gh authenticated;
an account *logged in* (registered is not logged in — the auth state is what
counts); voice keys; the systemd unit; lingering, without which the unit
starts at first login rather than boot; the board installed as an app. A
feature that needs setting up adds an item there the same way it adds a
dependency check. The card also offers to adopt sessions already running in
your own terminals — they are on the board the moment the fleet's first tick
sees them, but adopting one stops its process and resumes it inside
agentbox's tmux, so it is offered one at a time through the guarded adopt
path, never done on its own. `bun scripts/fresh-machine.ts` rehearses all of
it on a throwaway HOME; that rehearsal is how a setup claim is known to hold.

## Security

The server binds loopback and requires, on every mutating request, an
`x-agentbox: 1` header plus an Origin (when present) and Host that are
loopback. That blocks a web page in your browser from driving the API, which
v1 allowed. Skill paths are confined to the skill roots by realpath; skill
names are validated as a single path segment.

## HTTP API

Every response is `{ok, data, error}`. Every non-GET request must carry
`x-agentbox: 1`. `:id` is agentbox's short session id. Errors are 4xx with
`error` saying why (400 bad input, 404 no such thing, 409 not in a state to
do that); 500 is a bug.

WebSockets:

- `/ws` — server pushes `hot`, `cold`, `metrics`, `error`, and `timeline` for
  the one session the client `watch`es. `hot` (the open sessions) and `cold`
  are whole on connect; after that `hotDelta` carries only the open sessions
  that changed, each whole, and the ids no longer open, and `coldDelta` only
  the parts of cold state that changed. Closed sessions are not pushed: the
  See closed list pages them from `/api/sessions/closed`, and `closedStamp`
  moves when one is closed or reopened (`{"type":"watch","sessionId":…}`;
  `null` stops). The first timeline frame is `reset: true` with the newest
  page and a `before` cursor for paging back; then increments, each with the
  `cursor` to resume from. A tool event may be re-sent with the same id when
  its result arrives — replace by id; the re-sent event carries `endedAt`, the
  moment the result was written, so the UI can show how long the call took. With it, `btw`: the watched session's
  side questions, all of them (`items`), on watch and on every change. The client may also send
  `{"type":"ping"}`. `build` (`{"type":"build","entry":"index-….js"}`, on
  connect and after each `web:build`) names the UI build on disk; a page
  loaded from another reloads when that loses nothing (`web/src/lib/update.ts`).
  The server listens from its first second, before its first pass over the
  transcripts is done: until then a page's socket gets `starting`
  (`{"type":"starting","read":N,"of":M}`, on connect and every half second)
  and nothing else, a watch sent meanwhile is answered once the board is
  ready, every `/api/*` request but `/api/health` waits for that too, and
  terminal and voice sockets are refused with a 503. Just before it exits
  (SIGTERM, a restart) it sends `restarting` to every page and closes with
  code 1012; the page then retries every half second rather than backing off.
- `/ws/term/:id?cols=&rows=` — a live terminal on the session's tmux. Server →
  client: binary frames of raw terminal output; a session not in agentbox's
  tmux gets one text frame saying so and a close with code 4000. Client →
  server: text frames `{"type":"input","data":"…"}` and
  `{"type":"resize","cols":N,"rows":N}`. Closing the socket detaches; the
  agent keeps running.
