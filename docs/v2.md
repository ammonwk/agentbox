# agentbox v2

One place to see, start and continue every coding-agent session on this
machine — Claude Code, Codex, Devin, omp, opencode and Muse Code — across every subscription you are
logged into, with new sessions placed on whichever account has the most room.

This file is the contract between the pieces. If a change contradicts it,
either the change is wrong or this is: say which, in the same commit.

## What changed from v1, and why

v1 ran omp only, over ACP, in detached host processes, and let other agents
spawn omp agents as MCP subagents. v2 drops the omp-only host entirely. What
it keeps from v1: the subagent MCP (see below), skills management, the
machine and per-session load metrics, worktree reclaim, repos, PR lookup, the
router and the WebSocket split between hot state, cold state and metrics.

What it takes from switchyard: reading every provider's own transcripts as the
source of truth, tmux as the only way a session is driven, and adopt
(stop a CLI session, resume it under agentbox) with its check-before-kill
ordering.

v1's board chats were omp sessions, and omp kept its own transcript of each
all along, so they came over as ordinary v2 omp sessions: 114 of v1's 129,
imported by `scripts/import-v1.ts` (commit `7825eba`, since removed) with
their worktree and archive state; the rest never started a conversation.
v1's own data — `agentbox.db`, its per-session event logs and host logs —
is in `~/agentbox-v1-archive-2026-09-24.tar.gz`, and the last v1 commit is
tagged `v1`.

## A session is the provider's, not ours

Every provider already writes a durable transcript. agentbox never writes a
second copy of the conversation; it reads theirs.

| provider | transcript | live-process signal | resume |
|---|---|---|---|
| claude | `$CLAUDE_CONFIG_DIR/projects/<slug(cwd)>/<uuid>.jsonl` | `$CLAUDE_CONFIG_DIR/sessions/<pid>.json` (`sessionId`) | `claude --resume <uuid>` from the original cwd |
| codex | `$CODEX_HOME/sessions/YYYY/MM/DD/rollout-<iso>-<uuid>.jsonl` | `codex` pid, its `CODEX_HOME` from `/proc/<pid>/environ`, cwd, rollout mtime | `codex resume <uuid>` |
| devin | `~/.local/share/devin/cli/sessions.db` + `transcripts/<id>.json` | `session_locks/` | `devin -r <id>` |
| omp | `~/.omp/agent/sessions/<slug>/<iso>_<uuid>.jsonl` | `omp` pid + file mtime | `omp -r <path>` (by id if the file cannot be found: `-r <id>` searches, and from another project stops to ask about moving the session) |
| muse | `<XDG data>/muse/sessions/YYYY/MM/DD/<uuid>/session.jsonl` | native `muse` / `muse-bin-*` pid holding that session's `.session.lock` | `muse resume <uuid>`; a new prompt is typed after the TUI is ready |

Muse Code support is based on the installed 1.3.0 CLI and retained event
format. Its session stream supplies messages, mid-turn steering, tool calls
and results, reasoning summaries, token counts, compactions, errors and
rewound conversation turns. Reads are incremental and cached across restarts;
the separate run/task logs and approval-only side streams are not board
sessions. `muse exec` and `muse serve` are headless and are never adopted.
Model choices come from Muse's own cached catalog. Subscription quota windows
are unknown; agentbox does not fetch or refresh Muse tokens.

The database holds only what the provider cannot: which account a session is
pinned to, its claim on that account, the tmux session it
runs in, a label, when it was closed, and the metrics we collect for calibration.
A session row is keyed by `(provider, agentSessionId)` and gets a short
agentbox id for URLs.

## Every agentbox session is a real TUI in agentbox's own tmux

`tmux -L agentbox`, one tmux *session* per agent session, named
`ab-<shortid>`. One session each (not one window each in a shared session) so
that a terminal and a browser can both be attached without switching each
other's windows.

This is what makes "start in the CLI, continue in the app, and back" a
non-event: `agentbox claude` starts the agent in tmux and attaches your
terminal; the web UI attaches a PTY to the same tmux session and renders it
with xterm.js; detaching either leaves the agent running. The structured
timeline beside it comes from the transcript, not the screen.

A session started with plain `claude` in some other terminal is still
discovered from its transcript and shown read-only. **Adopt** moves it into
agentbox: prove the resume will land (transcript exists at the slug of the
resume cwd), SIGTERM the process, wait for it to exit, `--resume` in tmux on
the same account. Never kill first.

Input from the web goes through `tmux load-buffer` + `paste-buffer` (bracketed
paste, so multi-line text stays one prompt) and a separate `Enter`. Claude Code
gets it as many small pastes with the line breaks pressed as Ctrl+J
(`ProviderAdapter.pasteInPieces`): it sets a paste of more than 800 characters
or two line breaks apart as `[Pasted text #1]` and sends it to the model
wrapped in `<pasted_content>`, as text you did not write. Every write
targets the tmux session by name (`=ab-<id>:`), never a stored pane id — tmux
renumbers panes when its server restarts.

A session is `blocked` when it shows a prompt only you can answer, and that
is read from two places: Claude's own word (its status file says it waits on
a dialog), and the screen (each adapter's `blockedOn`). Neither is taken
whole. A dialog stands where the CLI's input box was, so with the box on
screen the words of one above it are the conversation quoting it — a turn
that ends "Do you want to proceed?", a diff of the file that looks for them —
and claude, codex and omp read only what is under the box (`underInput`,
`src/core/providers/tui-screen.ts`; devin and opencode still match anywhere).
A dialog the fleet answers is never yours: a start-up one (`autoAnswer`:
folder trust, the bypass-mode confirmation) and a permission prompt in a
session that skips them (`approvePrompt`) are pressed in the same pass that
sees them, and only when the keys have been ignored a few times is the
session blocked. Something already said to be blocked is looked at every
pass, not only once its transcript has been quiet.

A push (`src/core/push.ts`) goes out for a block that has stood five seconds,
so one that lasted a pass is never announced; and not for a panel you opened
by typing into the session's terminal (/model, /config), which is a dialog to
Claude, known by its bare "dialog open" within five seconds of your keys.

The composer keeps unsent drafts separate from pending submissions. Send
takes a specific draft revision into temporary browser storage before making
the request; returning or reloading never restores it as unsent. Newer edits
remain in the input and saved draft, including their agent guidance context.
Both chats keep a locally active delivery marked Sending; automatic and manual
receipt checks wait until that request has finished. A known
failure before delivery offers Restore draft, which preserves newer typing.
A missing response stays Delivery unconfirmed (shown no earlier than five seconds
after submission) and is checked against the
receipt and complete, recent transcript messages. Repeated identical
submissions require their receipts rather than guessing which one a transcript
message proves. Pending input is discarded on confirmation or explicit dismissal;
it is not another conversation history.

The keyboard follows the panes: Left moves out toward application navigation,
Right or Enter opens a list item, and Up/Down moves through lists. Session
parents still expand and collapse before leaving the tree. Tab and Shift+Tab
reach the controls within a page; F6 and Shift+F6 move between panes, including
from editors and terminals. Text fields keep their caret keys; Left at the
start of a search or composer moves out. Review's card actions use Shift+arrow,
so plain arrows can navigate without answering a card. A detail page returns
focus to the item that opened it (`web/src/lib/keyboard.ts`).

In text fields, holding Space for one second starts dictation. Keep holding
while speaking and release to transcribe into the current selection; Escape
cancels. Short presses type a space. The global handler (`web/src/Dictation.tsx`)
uses the same recording and transcription path as phone voice messages.
Changing focus or editing cancels the take, including a transcription still
in flight, so a late result cannot replace newer text. Terminal input uses
xterm's paste path with control characters removed, leaving the result for
review before Enter. Password fields keep their own keys. Dictation never
submits a field. On the first use, allow microphone access and hold Space
again if the permission prompt interrupted the hold.

Each composer submission has an ID. The server keeps only its session, a
payload hash, timestamp, state and error in `send_receipts`, never the message.
The attempt boundary is committed durably before typing or starting a CLI
with the prompt. A repeated ID returns its receipt instead of delivering
again; using the ID with another payload is refused. After a restart, a
queued submission is a known failure, and one past the attempt boundary is
unconfirmed. tmux and the receipt cannot commit together: uncertain delivery
is never automatically replayed. `/btw` confirmation means its side question
was recorded and queued, with its usual card tracking the answer.

An agent agentbox launches or resumes is told where it runs
(`src/core/providers/briefing.ts`), appended to its system prompt: claude and
omp by `--append-system-prompt`, codex by `-c developer_instructions`; devin
has no such flag. It says two things. An image named in Markdown,
`![what it shows](/tmp/shot.png)`, shows in the timeline, which reads the file
through `/api/sessions/:id/image`; the transcript keeps only the path. And
work that ends in a pull request or waits on CI goes to an agentbox session of
its own (`agentbox claude --detach`), not a subagent: a subagent holds its
turn open to wait, on a five-minute cache, may not read a message until it
finishes, and keeps its parent up for the hours a PR's rounds take. An
adopted claude session launched with an `--append-system-prompt` of its own
keeps that one instead.

Your own standing rules follow it: `<agentbox home>/rules.md`
(`~/.local/share/agentbox/rules.md`), when it exists, is appended under one
line saying whose rules they are, for every provider the briefing reaches.
It is read each time a session is launched or resumed, not when the server
starts, so an edit reaches the next session without a restart. The file is
yours: the repo never holds a name or a rule, and nothing in agentbox writes
it. Keep it short and change it rarely. Every word of it is in every
session's context, and each edit changes the system prompt of every session
resumed afterwards, which spends that session's prompt cache once. Only the
first 4 KB are read, cut at a whole line with a line saying so, so that a
mistake (a log redirected into it) cannot bloat every prompt.

A claude session is also launched with one hook, by `--settings` (it adds to
the user's own hooks): PreToolUse on the Agent tool
(`src/core/providers/claude-spawn-hook.ts`). Claude keeps every subagent of a
process in one flat list and resolves `SendMessage({to: "main"})` to the
top-level conversation, so a subagent's own subagents, told nothing of who
started them, wrote to the conversation the user was reading. When the one
spawning is itself a subagent the hook adds a line to the child's prompt naming
it as the one to write to. Every child's prompt also gets the same rule as the
briefing, from the other side: a subagent whose task leads to a PR pushes it,
hands it to a session of its own, and finishes. An adopted session launched
with a `--settings` of its own keeps that one.

`lastPrompt` and `lastPromptAt` describe the same delivered prompt, whether
sent by a person or another agent. They move together when the transcript
records it, including a message delivered mid-turn. Fleet housekeeping notes
are excluded. The board orders by this prompt time; parking uses activity
and cache clocks. An unavailable prompt timestamp falls back to the session's
start in the API.

## The backend without a terminal

`agentbox service install` installs the backend with the platform's service
manager for this checkout. On Linux it enables the systemd user service and
lingering (boot before login). On macOS it writes
`~/Library/LaunchAgents/local.agentbox.server.plist`, bootstraps it in the
user's GUI domain, and keeps it running from login onward. The installed
Chrome app and ordinary browser URLs then have a backend ready whenever they
open. A login shell supplies the environment; credentials are never written
into the service definition. On macOS `AbandonProcessGroup` preserves agent
processes when the backend restarts.

`agentbox start` starts the backend in the background if it is down, using
the installed service first. Without one, a detached process works on either
platform. `agentbox kill` stops the service (on macOS, bootout), leaving the
agents running; `start` brings it back. Restart an installed macOS backend
with `launchctl kickstart -k gui/$(id -u)/local.agentbox.server`. The server
log is `<agentbox home>/logs/server.log`.

## Machine cleanup

The heartbeat button at the right of the system bar pauses live sessions and
starts one cleanup agent. `src/core/cleanup.ts` owns this operation. It suspends
each agent and its descendants, preserving their in-memory work; it does not
free that memory. The cleanup agent investigates CPU, memory, swap, disk and
containers, and may gracefully stop proven abandoned workloads while protecting
the paused agents and their dependencies. Ambiguous or destructive changes
remain the user's decision. The helper uses an available installed provider and
that provider's configured model.

The pause gates Fleet mutations, automatic recovery, retries, parking and
scheduled starts. Completed waits remain deliverable when sessions resume.
`cleanup.json` in the Agentbox home records only session IDs and suspended
process identities (PID plus start time), written before each suspension so
a server restart cannot strand them. Processes already stopped are left alone,
and Resume never signals a reused PID. The server and its ancestors are excluded.
The control opens the cleanup conversation; its play button stops the helper
and resumes only the processes this operation suspended. A failed start rolls
back the pause. Duplicate starts reuse the same helper. The pause stays in
effect across server restarts and until the user resumes.

## Parking idle sessions

An idle Claude process still costs 1–2% of a core and ~240 MB (measured: 82
idle ones held 1.4 cores and 19.6 GB). Once a session has been idle for
`parkIdleMin` (60; 0 turns it off) and its prompt cache has gone cold (see
"The prompt cache" below), keeping the process buys nothing, so the
fleet stops the process — "parks" it — and the next message resumes it with
that message as the prompt. A parked session keeps `status: "waiting"` (it is
still your move) with `host: "none"` and `parkedAt` set; stopping one
yourself makes it `stopped`. Claude sessions in agentbox's tmux only; never
one showing a permission prompt, never one with a
terminal or browser attached, and never before its resume is proven.

The unit is the tmux session: a lead's teammates are panes in it and are
stopped with it, so all of them must be idle. A turn that has been silent for
two hours counts as idle whatever Claude's status file says — it says "busy"
for days on a lead with teammates.

Anything that would wake the session later is a *hold*, shown on the session
as `parkHold`: a background command that will finish, a Monitor (its output is
messages to the session), a `/loop` wakeup still due, a cron job (one-shots
until they fire), in-process subagents that wrote in the last thirty minutes,
subagent-MCP agents still running (not finished ones holding an uncollected
answer), a teammate mid-turn or recently active, or CPU use above an idle
Claude's. Background processes that can never finish do not hold: bare log
followers (`tail -f`, `journalctl -f`, `watch`) and `while true` loops with no
way out, while they are between rounds; dev servers and tunnels hold for four
hours. A command that has only been sleeping between polls holds for a day
of quiet (a condition that can never come true looks the same forever); real
work holds for as long as it runs. A literal `until ! pgrep -f "…"` waiter
with only sleeps in its loop is a follower: its own parent shell matches the
pattern, so it can never finish. This also covers a file test joined with
`&&`, but not alternative conditions, regex tricks or filtered process checks.
Warming prompts and their replies refresh the cache, but do not reset the
quiet clock for polls and services. Timers set by an earlier process of the
session died with it and hold nothing. A session is parked only after
two clean checks a minute apart with nothing written or started in between,
and teammates stopped with a lead are named to it in its next prompt. The
rules are in `src/core/park.ts`.

One thing a session waits on can finish without waking it: Claude queues the
notification of a background command and never delivers it when an in-process
teammate started the command and has since gone idle. The lead then sits
"waiting on CI" with nothing running, and would be parked. A Claude session
quiet for 55 minutes (five before parking, where `parkIdleMin` is shorter),
or whose cache is about to go cold, with such a notification still queued
and its turn over — however many turns it has run since the notification
came, since a teammate reporting in wakes the lead without delivering it — is
sent one message naming what finished and where its output is
(`Fleet.keepWarm`; `stranded` in the transcript's facts). It is not parked
until it has been told, and the nudge in its transcript is the record that it
was. A session whose last try hit a usage limit, with no answer since, is
neither told nor held up for it (`Session.limitHit`): the nudge would only meet
the limit again, and continuing it is the limit banner's.

## The prompt cache

One clock says when a session's prompt cache goes cold, `Session.cacheWarmUntil`
(`src/core/cache.ts`): its newest model call — not its newest line, since
notifications are written for hours with no call behind them — plus the
lifetime that call wrote the cache with. Claude says which in each call's
usage (`cache_creation.ephemeral_1h_input_tokens` or `…_5m_…`): an hour on a
subscription, five minutes on an API key or in usage overage. A provider
that does not say gets `balancer.claimIdleMin`. Everything that asks whether
a cache is warm reads it: `cold` and the account pin, a claim lapsing,
parking, and the order crash recovery resumes in.

A Claude session in agentbox's tmux whose turn is over and that is waiting on
work that will wake it — a background command, a monitor, a wakeup,
subagents: what a crash would take — is sent a one-line message five minutes
before an hour's cache goes cold (`Fleet.keepWarm`, `keepWarmNote`), so the
work wakes it to a warm cache. Reading a cached conversation back costs a
tenth of an input token per token, and rewriting it after an hour two; a
350K-token session woken by its CI an hour and twenty minutes after its last
call rewrote all of it. Not for a five-minute cache (it would take a message
every few minutes), not to a session stopped at a usage limit, at most eight
in one wait, and never again before the last one is answered. The count is
folded from the provider's transcript, survives server restarts, and resets
only on real activity (a prompt, notification or tool call), never on a
warming reply, however long that reply takes. The message
asks for one line saying what the session is still waiting on, which the
board then shows as its last word. agentbox's own whole-message notes
(`[agentbox: …]`) are shown as agentbox's and are not counted as something
you said (`readSent`).

## Crash recovery

A crash stops every agent at once — the machine restarting, your user's
systemd being stopped (a logout, or a stray SIGTERM), agentbox's tmux server
dying — and with them every background command, monitor and subagent they
were waiting on. Recovery brings back what the crash took, and only that
(`src/core/recovery.ts`).

The fleet writes down what every running session is doing as it goes:
`$AGENTBOX_HOME/live-sessions.json`, rewritten whenever a session starts,
stops or changes state, and once a minute regardless. Per session: where it
runs, its status, what it is waiting on you for when blocked, and — with its
turn over — the work it is still waiting on, judged by the parking rules (a
background command, a monitor, a wakeup, subagents; a dev server does not
count). A session in another terminal is written down with its launch flags
and its shell's variables; a run another session started (a teammate, a
`claude -p`) is not, since it comes back with that session or not at all.

A crash is proven, never guessed from one session being gone: since the
snapshot, the machine booted, your user's systemd is a different process, or
the tmux server is. Checked when the server starts, against the previous
run's snapshot, and on every pass after. The tmux server dying alone takes
only what ran in it; a session in another terminal that is gone was closed
there. A session stopped by you or by the fleet, or parked or closed since, is
left alone. One whose process is still exiting — hung up on by the tmux
server's death, and seconds from gone when mid-turn — went with it all the
same: recovery waits for that process to go before resuming it. Then, per
session:

- **resume** — mid-turn, or its turn over but waiting on work the crash
  killed. Resumed on its own account, warmest cache first, three seconds
  apart, with a prompt saying what happened: its background work is gone, and
  any address it held for another session is stale.
- **park** — its turn over with nothing running, or waiting on you (a
  question, a permission). `status: "waiting"`, `parkedAt` the time it was
  last seen; your next message resumes it. One that was waiting on you is
  told, in that prompt, that the dialog is gone (`parkedWhy`).
- **revive** — a subagent-MCP agent that was mid-turn or holding an
  uncollected answer comes back through its caller's resume (see Subagent MCP).
  A finished one is left.

A crash more than a day before the server notices it parks everything. The
report — each session, what was done and why — is saved in
`$AGENTBOX_HOME/recovery/<ms>.json` and logged; an executable of yours at
`$AGENTBOX_HOME/notify` is run with its summary as the one argument, to relay
it to wherever you will see it (`AGENTBOX_NOTIFY=0` turns that off). `agentbox recover`
shows what a crash now would do; `--last`, the last
recovery; `agentbox recover <id>...` recovers stopped sessions by hand, as they
were last seen running.

Every session the fleet starts or resumes is then watched for ten minutes:
two tool calls refused by a permission rule ("User skipped this tool call")
mean it came back unable to act — it reads the refusals, concludes it cannot
do its job, and stops. A devin session is stopped and resumed once with its
saved permission mode fixed (devin resumes in the mode `sessions.db` saved
and ignores `--permission-mode`; the adapter's `prepareResume` sets it before
every resume); anything else is shown `blocked` with the reason, and a
recovery's report says so.

## Sessions that start sessions

Agents start agents: a lead's teammates, a `codex exec` or `claude -p` run
from a Bash tool, a session that runs `agentbox codex --detach`. Each is a
session of its own, and a release or a babysit can leave dozens. A session's
`parent` is the session that started it; the board and `agentbox ls` list a
child under its parent, folded by default. The sidebar expands the selected
session and a hovered or keyboard-focused session with a slide-open reveal
(respecting reduced motion), keeping ancestors open while moving into children; its expansion button keeps children visible after moving away.
Once its parent is closed or gone, a child
that still runs shows at the root, and a stopped one is shown closed
(resumable by id) rather than stranded there. The fleet records it once,
from proof, never from titles or paths (`Fleet.linkParents`):

- **Claude teammates.** A member stamps `teamName` on every record; its
  lead's transcript has a `teammate_spawned` tool result naming the same
  `team_name`. (The team's `config.json` also has a `leadSessionId`, but it is
  not the lead's transcript id, so it is not used.)
- **The process tree.** A running session whose process has another
  session's process above it is that session's child — but only if its
  conversation began under that process, so a session merely resumed from
  inside another is not claimed. Provider environment variables are no help
  here: `CLAUDE_CODE_SESSION_ID` is inherited by the agentbox and tmux servers
  from whichever session last restarted them, so every pane carries a stale
  one.
- **The API.** `POST /api/sessions` takes the caller's pid (the CLI and the
  fleet MCP send theirs), and the session above it is the new one's parent.
  A detached orchestrator, whose process tree no longer reaches the session
  it works for, names the parent outright (`parent`), and `PATCH` sets or
  clears one after the fact.
- **You.** Drag a row onto another on the board to put it under that one, or
  out from under its parent to the top level (`PATCH` with `parent`). That
  parent is yours (`parentByHand`): the fleet never links the session again,
  and it is a grouping, not a run its parent made, so it is not shown closed
  when it stops. A subagent cannot be moved: it stops with the session whose
  MCP runs it.
- **Subagent-MCP agents.** Each records the session that asked for it
  (`owner` in its `meta.json`), which wins over the process tree. See
  [Subagent MCP](#subagent-mcp).

What cannot be told: a child whose parent's transcript is gone, one
that ran and stopped before agentbox saw its process, and work handed to a
detached daemon (the Codex plugin's shared app-server broker). Those show at
the root. Stop and the rest act on exactly the ids they are given; close
takes the sessions a parent started, at any depth, off the board with it —
running ones are stopped, the parent first (its death takes its MCP servers
and the pool agents they run), and the app asks first when any are running.

## Messages between sessions

`agentbox send` and the fleet MCP's `send` type one session's words into
another (`POST /api/sessions/:id/send` with `from: "agent"`). Two things are
refused there, in the route, with a message the sender can act on
(`src/core/sendguard.ts`). They live in the tool because the same rule
written into prompts was broken as often as it was stated.

- **Taken over.** A session another has taken over (a schedule's
  replacement: its `successor`, set by `Fleet.handOver`) is not who the
  sender means any more. Its workers still hold its id, and one that
  answered a refusal with `--wake` brought a replaced steward back, so two
  merged at once. The message goes to its heir instead (`Fleet.heir`, the
  last in the chain), marked `[sent to <old id>, which you took over from]`,
  and the sender is told where it went and to send there from now on (the
  route returns `{to}`). The refusals below are the heir's, and `--wake`
  never reaches the old one. You can still type into it yourself.

- **Waking.** A message to a session that is stopped, parked or closed, or
  whose prompt cache has gone cold (`cacheWarmUntil`, for every provider),
  makes it read its whole context again at full price to hear one line. It is
  refused, naming the context size and what to do instead: read it
  (`agentbox show`, `agentbox log`), start a fresh session with a handoff if
  its work must go on, or send again with `--wake` (`wake: true`) when waking
  it is the point: the answer to a question it asked, a blocker only it can
  clear. With it a stopped or closed one is resumed with the message, which
  from you is an error ("resume it first"). A session mid-turn is never refused for this: the message joins a
  turn that is paying for the context anyway.
- **A limit not yet over.** A session stopped at its account's usage limit
  carries when the limit lifts (`Session.limitHit.until`: the reset of the
  account's spent window; the wait or the date the provider's message names
  only where no window of the account ever accounted for the hit). Until then
  every message is refused by the provider the same way,
  so an agent's send is refused here first, naming the time; `--wake` does
  not lift it. The fleet's own nudges wait for the same moment. A script that
  retries sessions should read `limitHit.until`, not parse the message: one
  that read only "reset in N minutes" retried six sessions every two minutes
  against a weekly limit five days off.
- **Chatter.** More than 3 messages from one session to the same session in
  an hour are refused, saying when the next has room and to put what is left
  into one message. Of 185 sender and reader pairs in the transcripts the
  number was picked from, 175 never passed three in an hour; the ones that
  reached five and six were coordinators narrating to workers. `--wake` does
  not lift it. The counts are in memory, so a restart forgets them.

A refusal is HTTP 409 and nothing is typed, so `agentbox send` exits 1 with
the reason and the MCP tool fails with it: a refused message never looks
delivered.

A message from an agent on another machine (the cloud, below) passes the same
checks (`agentRefusal`), with each remote agent as one sender. It is framed as
a peer's untrusted message, its refusal goes back to its sender, and it is
typed at most once ([docs/cloud.md](cloud.md#messages)). Neither applies to you (the app, the terminal, voice mode's
`AGENTBOX_SEND_AS=you`) or to what the fleet types itself: keep-warm notes,
recovery notices, a schedule's notes.

## Cards

A session can hand you something to decide or to know, and your answer goes
back to the session that asked (`src/core/cards.ts`, `agentbox card`). It is
how a session that works for hours without you asks its questions in one
place, instead of in a conversation you would have to read to find them.

A card has a kind (`decision`: you owe an answer; `merged` and `note`:
something happened), a title, a short version of two or three sentences, and
optionally a long version in Markdown, a pull request, what the asker
recommends, and a default with a time. It remembers the session that added
it. A `key` makes adding idempotent: the same key again returns the card that
has it. Cards are yours, not a conversation, so they are the `cards` table.

The Review page shows them one at a time from a stack. Every decision not
put off comes before every card that only reports, whatever its age: those
with a default and a time first, soonest on top, then the rest oldest first;
under them what happened, oldest first (what has waited longest is met
first, in every group, and in the Later list). Later means later: a decision kept
for later goes under the reports, so they can be reached, and comes up again
when the stack gets round to it, or at the top once its default's time is
within two hours or has passed. Reports kept for later are last. Right (or →)
opens a sheet to answer; left (←) keeps it for later, at the back of the
stack and under Later; up (↑) opens the long version, from which the others
work; down (↓) approves: on a decision the asker's recommendation becomes
your answer ("Go with your recommendation."), on a card that only happened it
means seen, and a decision with no recommendation springs back and says there
is nothing to approve. Each has a button, and the last one can be undone (u). Answered and
withdrawn cards are under Done with what you said. The nav's count is the
cards you have not yet seen (open, not kept for later).

Your answer is typed into the asking session as your own words, `[card 12
“title”] …`, by the send path, which wakes a parked session and resumes a
stopped one. It is held 8 seconds first, which is the undo; once typed it
cannot be taken back. An empty answer means "seen" and is typed nowhere, so a
stack of merged cards does not wake its session once per card; a decision
cannot be answered empty. When the asking session is gone or closed the
answer waits on the card as unread: `agentbox card list --answered --unread`
shows it to whichever session asks, and `card ack` says it has it. A
same-session schedule that replaces its session gives the old one's open
cards and unread answers to the new one, as it does its children.

A new decision is pushed to your devices by the path a blocked session uses
(`src/core/push.ts`): one push for all that arrive within 20 seconds, and
never for a card that only happened. A decision's default and its time are
the asker's to act on; agentbox only marks that the time has passed.

## Who has a pull request

One answer, held where the sessions are (`src/core/prclaims.ts`), so that
nothing guesses it from prompts, titles or a script's own ledger, and no two
sessions work the same PR. A live session (running, waiting or asking) has a
PR in one of two ways:

- **It is on the PR's branch**: what `PrInfo.sessionId` has always matched,
  for the open PRs of registered repos. The session that opened it has it.
- **It said so**: `agentbox pr claim <n|owner/repo#n|url>` from inside it
  (`--for <id>` to say it for another), or `--claim <n|…>` when it is started
  (`POST /api/sessions {claim}`), which gives it the PR before it exists to
  anyone else: a second start on the same PR is refused. This is how a session
  in a detached worktree, or one sent to fix a PR another opened, has it. What
  was said wins over a branch.

A claim is refused (409) while another live session has the PR, and the
refusal names that session as another, how it holds it, and the asker;
claiming what the session already has succeeds (`already` in the answer) and
the CLI says "you already hold". Whatever names the caller says so in words
("you", "(you)" after its id in `pr who`, `pr claims`, `ls` and `show`, `you`
in their JSON; `POST /api/whoami` when `AGENTBOX_SESSION` did not reach the
command): a session reads its own id like any other, and j2g254q4, told
"#8154 is j2g254q4's", stood down from four PRs it held itself. The
CLI speaks for the session in `AGENTBOX_SESSION`, as `send` and `card add` do,
and the server walks up from the caller's process only when that did not reach
it (Codex runs commands without it). Nothing is cleaned up when a
session stops or closes: its claim simply stops counting, and counts again if
it resumes and nobody took the PR meanwhile. `agentbox pr release` lets go of
the named PR, including a branch hold. Release records that exclusion durably
and atomically cancels its armed PR waits and any completed results not yet
delivered. It does not wake the former holder. Branch discovery cannot restore
the claim; an explicit successful claim can. Taking a stopped session's claim
has the same release effect. A former holder cannot re-arm that PR's wait.
Messages, schedule notes and every resume carry the current release notice at
the delivery boundary, including messages queued before the handoff. A wait
already entering delivery can therefore report no authority to act. Independent
observers may still wait on PRs they have never held. On a
same-session replacement the successor gets the claims, as it gets the
children and the cards.

A holder can explicitly hand off with `agentbox pr transfer <repo#n> --expect <holder> --to <successor>`. The local server authenticates the holder with its private session capability, requires the expected current holder and a live independent destination, and records an explicit claim. It also works when ownership came from a startup branch that is no longer current. A stale competing transfer is refused. The same transaction revokes the former holder and cancels its PR waits; other session, card and wait handovers still use the fleet handover.

`agentbox pr who <n>` answers for one PR (exit 1 for nobody), `agentbox pr
claims` and `AppState.prClaims` for all; `PrInfo.owner` is the same answer on
each open PR. A bare number is a PR of the repo the command is run in.
Reading or reviewing a PR is not having it and needs no claim.

## Waits

A session waits on things outside its turn: a pull request's checks, a merge,
a deploy, a production job, another session. Left to itself it waits with
whatever it can write (a background loop over `gh`, `gh run watch`, a
`pidwait` and a message, a monitor), and each of those lives in the session's
own process tree. It dies when the session is parked, moved or restarted, and
it can end without the event and without a word: a loop whose two conditions
were never true in the same poll, whose timeout printed what success prints;
a waker killed with the shell that started it; a job stopped with the idle
session that owned it.

A wait (`agentbox wait …`, `src/core/waits.ts`) is a row the server owns. The
session arms it and is free: to end its turn, to be parked, to be moved. The
server looks, and the wait ends in exactly one of four ways, typed into the
session as agentbox's own note (`[agentbox: wait 12 (…) ended: HAPPENED. …]`)
by the path a schedule's note takes, so a parked session is resumed with it:

- `happened`: the checks concluded on the head (a failing one ends it at once
  and is named), the pull request merged, the run or job ended (its
  conclusion, or the job's recorded exit or signal, with the end of its output), the
  command exited 0, another session's turn ended.
- `stuck`: waiting can no longer bring it. The head moved off the one waited
  on (for a merge, only when `--head` named one), the pull request was closed,
  or a check wait needs workflows that merge conflicts prevent from starting.
  Otherwise, a named check has not reported while
  nothing on the head has been running or queued for 30 minutes (a review
  that gave up; a workflow that never started).
- `timeout`: its deadline came first. Every wait has one, and one whose
  deadline passed gets a last look before it is called a timeout.
- `broken`: it could not be watched. Every look failed for 20 minutes, an
  `until` command failed five times running (any exit but 0 or 1, or an exit 1
  with an error on stderr: a test after a read that failed is not an answer), or a job's unit is gone and left
  no result (a reboot or a native stop without recorded completion).

What it looks at (`src/core/waitreads.ts`): every pull request waited on in
one GraphQL request each 90 seconds (state, head, base, mergeability, the head
commit's check runs and statuses); a run by a conditional GET each minute, which costs
nothing while it has not changed; a job by the result file its unit's
`ExecStopPost` writes, else `systemctl is-active`; on macOS its runner writes
the same result format, otherwise `launchctl` supplies running state or
failure evidence. Completed macOS jobs are unloaded after their evidence is
saved. An `until` command is read by running it, as a schedule's note command
is run; a session by the board.
GitHub's rate limit running out is not a failed look: nothing is asked until
the reset it names, and the deadline still stands.

Each `until` probe runs at low priority in its own POSIX process group, with
a server-owned two-minute deadline on macOS and Linux. Expiry kills the probe
and its children and counts as a failed look, never an event. Output retention
is bounded. No external GNU `timeout` command is required. Exit 0 means the
event happened; exit 1 with no stderr means not yet. Other exits and exit 1
with stderr report a failed look.

A check asked for by name must be there: "every check concluded" is true of a
head no workflow has reached yet, and a review that posts a status only when
it has read the head is waited for by that name (`--require 'Reviewed head'`:
every check, and that one among them; `--only` waits for just the named).
`Merge gate` is merge authorization owned by the steward, so it is excluded
from PR check waits, counts and diagnostics, regardless of its state. Naming
it with `--require` or `--only` is refused; `--merged` still waits for the
actual merge. The owner finishes CI and review and reports readiness to the
steward without waiting on merge authorization.

`--feedback --head <sha>` is a separate PR wait on submitted reviews, inline
comments (including replies in resolved threads), conversation comments and
failed checks. It wakes on existing feedback at the first look, then on new or
edited feedback when rearmed, even with other CI queued. It does not interpret
the verdict or declare readiness; `Reviewed head` success does not prove clean
review. The owner reads and dispositions the actual GitHub surfaces. Each look
paginates at most 1000 records per surface; incomplete/unavailable reads report
failure, never unchanged feedback. Only digests and check identities are retained.
The ending and cursor persist atomically; rearming the same owner's PR/head
carries its cursor across restarts. A released owner's waits remain cancelled.
Every check with no names is believed on a second look 80 seconds after the
first, since workflows register one by one. A wait for every check ends with
the conflict and the base to resolve against as soon as GitHub reports it:
`pull_request` workflows cannot start on a conflicting PR, even when external
checks pass. Unknown mergeability is still unknown, never a clean result.
`--only` can wait for named checks that already exist despite conflicts; a
missing name gets the conflict diagnosis. A `--merged` wait still follows the
merge itself, since the owner can resolve conflicts while another session waits.

`agentbox wait job -- <command>` starts the command in the caller's directory
and environment: a systemd user service on Linux (`agentbox-job-<id>.service`),
or a one-shot launchd agent on macOS (`gui/<uid>/com.agentbox.job.<id>`, using
the user domain when no GUI domain is available). It is outside the caller's
process tree, so stopping, parking or moving the session and restarting the
server leave it running. One argument is a shell line; multiple arguments
are an argv. Output and results stay under `<agentbox home>/jobs/`, at the
paths printed by the CLI. `unwait` cancels notification, not the command;
the CLI prints the native command to stop it separately.

On macOS the environment is a private 0600 snapshot in a 0700 job directory,
deleted before the command starts. The plist contains paths, not credentials.
The runner records an attempt durably before starting work and never repeats
it, even when launchd is kickstarted or its plist reloaded. Jobs are not
installed for login or reboot. A missing job without a result is unknown,
never successful; a signal is named only when the runner or launchd reports
it. A definite wait-registration refusal stops the command's process group.
A lost or malformed response, or a server error, leaves registration
unconfirmed: inspect the wait and its printed evidence before acting, and
never automatically rerun the command.

Telling can wait; ending cannot. A session that is closed, was stopped by
hand, or is stopped at a usage limit is not resumed for it: the wait shows
`NOT TOLD` with the reason in `agentbox waits` and is typed in when the
session next runs, for a day. A session's successor hears what its
predecessor armed. Closing a session cancels what it was still waiting on.

A restart of the server ends no wait: they are rows, and the first tick looks
again. `agentbox waits` is also how anyone else (a steward, you) sees whether
a session that says it is waiting has anything armed.

## Schedules that speak to one session

A recurring schedule starts a new session each time. Two things change that,
for one that repeats at a time ("every 10 minutes", "every weekday at 9am";
`src/core/scheduler.ts`, `come`):

- **A note command** (`noteCmd`). Each time the schedule comes due the
  command is run by `sh -c` in the schedule's directory, at the lowest
  priority, for at most two minutes, with `AGENTBOX_SCHEDULE` (the schedule)
  and `AGENTBOX_SCHEDULE_SESSION` (the session it spoke to last) set. What it
  prints is the note, said before the schedule's prompt as a red rule's note
  is. When it prints nothing, nothing happens that time: no session, no
  error, and `lastRunAt` does not move. When it fails or runs out of time
  that is the schedule's `lastError`, and nothing starts. The command should
  print what is true now, not what changed since it last ran: a time that is
  skipped is not made up.
- **The same session** (`sameSession`). Instead of starting another, the note
  (the prompt, when there is no note command) is typed into the session the
  schedule started last, marked `[via agentbox schedule <id>]` so it is not
  counted as you, by the path the fleet's own nudges take: it never moves the
  session to another account, and a stopped or parked one is resumed with
  it. While that session is mid-turn or showing a prompt the time is skipped:
  the command is not run, nothing queues behind a working session, and the
  next time says what is still true. When that session is gone, closed,
  stopped at a usage limit, or holds more context than `freshOver` (tokens;
  150k unless the schedule names another), a new one is started with the
  note, the prompt and a line naming the one it follows, and the old one is
  handed over and closed once the new one is up — alone. Handed over is at
  once: the new one becomes its `successor`, so an agent's message to the old
  id goes to the new one ([Messages between sessions](#messages-between-sessions)),
  and its cards and pull request claims move too. One that got busy in the
  moments the new one took to start is closed once that turn is over (the
  schedule's `retiring`, tried each tick, which hands over again whatever
  that turn added). The sessions it started (an
  `agentbox claude --detach` from inside it is its child) are first put under
  the new one, as a parent by hand, and named to it; closing a session
  otherwise takes what it started with it, and those may be hours into a PR.
  So the session lives long enough to keep its
  cache warm between notes, and never grows into one huge cold context.

A session started this way is an ordinary session: it has its own id in
`AGENTBOX_SESSION`, shows on the board, and can be typed into, stopped or
closed like any other.

## Accounts

An account is a provider plus a credential home:

| provider | isolation | default account |
|---|---|---|
| claude | `CLAUDE_CONFIG_DIR=<home>` | `~/.claude` (env unset) |
| codex | `CODEX_HOME=<home>` | `~/.codex` |
| devin | `WINDSURF_API_KEY` read from `<home>/devin/credentials.toml` (login runs with `XDG_DATA_HOME=<home>`) | the default XDG dir (env unset) |
| omp | an OpenCode Go sign-in, put on each request by the bridge | none: every account is one you added |
| opencode | none of its own: its sessions run on omp's accounts | — |
| muse | `XDG_CONFIG_HOME=<home>`, `XDG_DATA_HOME=<home>/data`, `XDG_CACHE_HOME=<home>/cache`, `TBH_CREDENTIAL_BACKEND=file` | default XDG config root (usually `~/.config`), with the normal XDG data root and credential backend |

A Muse account home is the XDG **config root**, containing `muse/auth.json`.
Dedicated accounts use Muse's file credential backend so separate logins do
not overwrite the default macOS Keychain item. `muse login` runs in that
account's environment; credentials and transcripts are never shared. Only
`muse/settings.json`, `muse/skills` and `muse/AGENTS.md` are linked from the
default config root. An inherited `META_API_KEY` is removed so it cannot
override the selected account. Muse sessions stay pinned to their original
home; its session index and associated files are not moved between accounts.

An omp account is an OpenCode Go sign-in, and opencode holds no account of
its own: both CLIs run on Go, so an opencode session is placed on, pinned to and
claims against an omp account, and the balancer weighs omp and opencode
sessions together. `accountProvider()` (`src/core/providers/account.ts`) is
the one place that says so; `Account.provider` is an `AccountProvider`, which
leaves opencode out, and every lookup from a session's provider to accounts
goes through it. Adding or importing an opencode account is refused with a 400.

Every account is an OpenCode Console sign-in, kept alone in
`<home>/opencode-console.json` (`src/core/accounts/gocred.ts`): the device
flow `opencode auth login opencode` runs, done by agentbox so the login is the
account's own. omp has no default account: you add each one and can forget
any of them, and the `opencode-go` API key the CLIs hold without agentbox
(`~/.local/share/opencode/auth.json`) is not an account and is given to no
session agentbox starts. Both CLIs keep one session store whatever account a
session is on (`ProviderAdapter.sharedStore`), so one account's listing is
everyone's, and a session whose account was forgotten resumes on the
balancer's pick (`Fleet.accountFor`).

Neither CLI can be handed a Console sign-in: opencode uses its own stored
login whatever its config says, and signed into a Console workspace it bills
that workspace. So every session
reaches Go through the bridge (`src/bridge/devin.ts`, `goProxy`), which puts
the account's credential on each request:

- `/go/<account id>/v1/…` → `opencode.ai/inference/go/openai/v1/…` with the
  account's Console token and its workspace (`x-opencode-org-id`). The bridge
  refreshes the token a day before it runs out, or when it is refused — and
  only the bridge does, since a refresh replaces the refresh token.
- `/go/<…>/anthropic/v1/…` the same for the Go models that speak Anthropic's
  API, which the Console gives an endpoint of their own
  (`src/core/accounts/gomodels.ts` keeps the list).
- A replayed tool call whose `arguments` do not parse goes upstream with
  `{}` (`src/bridge/toolargs.ts`). A model sometimes emits a noise call (no
  such tool, empty arguments); the CLI rightly keeps it in the history, Go
  refuses every later request that carries it ("400 `arguments` must be
  valid JSON"), and without this one bad call ends the session, a continue
  included.
- Reasoning another account issued is left out (`src/bridge/reasoning.ts`).
  A Responses model's hidden reasoning is an `encrypted_content` blob the CLI
  replays with the history, and Go takes a blob back only from the sign-in
  it gave it to ("400 reasoning `encrypted_content` was not issued to this
  caller"), so a session woken on another account was refused from its
  second turn on, a continue included. The bridge sends a refused request
  again without its blobs (a summary stays, as plain text) and remembers
  them, so the session's later requests go out right the first time.
- `/go/caller/v1/…` for omp, whose endpoint is fixed in
  `~/.omp/agent/models.yml`: a key of `agentbox-account:<id>` names the
  account, and any other is a real key, sent by an omp in your own
  terminal, that goes through untouched to `opencode.ai/zen/go/v1/…`.

opencode is pointed there by the `baseURL`s in the config its launch adds
(`OPENCODE_CONFIG_CONTENT`); omp by `models.yml`, whose `opencode-go` and
`opencode-go-responses` blocks have the bridge as `baseUrl` and
`OPENCODE_GO_API_KEY`, else opencode's key, as `apiKey` — the adapter sets
that variable to the account's name for every session. An omp in your own
terminal goes through the bridge too, on the key its `models.yml` found,
which is no account: it is filed under the first OpenCode Go account, and
the server starts the bridge with itself for it.

Each adapter owns its provider's homes and environments: `defaultHome()`,
`accountCommand()` for running a session, and `authEnv()` for the CLI's own
login and status commands (the same, except devin's XDG variables).

devin records no account per session, so its sessions are all listed under
the default account; one agentbox started on another account is matched back
to that account when it spawns.

Non-default homes live in `~/.local/share/agentbox/accounts/<id>/`. Shared
configuration is symlinked in from the default home so every account behaves
the same: for claude `settings.json CLAUDE.md skills agents commands plugins
hooks output-styles statusline* keybindings.json`, for codex `config.toml
AGENTS.md skills rules prompts hooks.json`, for devin `config.json` into
`<home>/config/devin/`. Credentials, `.claude.json`, transcripts and codex's
sqlite state are never shared. A new claude home gets its own `.claude.json`
seeded from an allowlist of preference keys in `~/.claude.json` (onboarding
done, theme, `mcpServers`, completed migrations) so it skips the first-run
screens; identity, usage cache and per-project state are never copied.

Transcripts are deliberately **not** shared between accounts. Sharing them
would let `claude --resume` pick up another account's session, which is
exactly the cache invalidation this whole feature exists to avoid.

A session is pinned to its account only while its prompt cache is warm.
Once its cache has gone cold (`cacheWarmUntil`, above) it is `cold`: the board shows it on "any account", and when it
is woken — resumed, or sent a message — the balancer places it like a new
session. If that is another account, `Fleet.wake` proves the resume (cwd,
transcript), stops the process if one is idle in tmux, **moves** the
transcript into the new account's home (claude: the `.jsonl` and its sibling
directory, plus file-history, session-env, tasks and todos keyed by the
session id; devin, omp and opencode: nothing to move, every account shares
one store and only the key differs), records an `assignments` row, and
resumes there with the message as the prompt. A move that fails resumes on
the old account. Codex keeps sessions in sqlite state as well as rollouts, so
it does not move.

A session that stopped at its account's limit (`limitHit`: the provider's
limit message is the last thing the model was asked and did not answer,
whatever was queued behind it since — `limitStop` in `park.ts` — and the
account's usage does not say the limit is gone) is moved by
the fleet once in its life (`Fleet.continueStalled`, `sessions.hopped_at`;
below). Claude also puts a dialog up at the limit (stop, wait here, add
funds): `blockedOn` names it `LIMIT_DIALOG`, and it is not a prompt for you
— the session is `waiting` with its `limitHit`, never `blocked`, and Esc
puts the dialog away before anything is typed into it. After the move, or
with nowhere to go, the UI offers "Continue on <the balancer's pick>", which
is `POST /api/sessions/:id/move` with the prompt "Usage limits have reset,
continue". `agentbox move <id> [--account NAME]` is the same request from an
agent, with `must`: refused when it would not change account, and for a warm
session that is not at a limit unless `force`. With no account named, a
session at its limit goes where the fleet's own move would send it.

A session whose turn ended on the provider instead of finishing (`turnError`:
`{at, kind, detail}`) also stopped without meaning to. `kind` says what a
retry is worth: `output-cap` — the reply was cut off by the model's max
output tokens (devin's `finish_reason: "max_tokens"`, Claude's "response
exceeded the 32000 output token maximum") and a message continues it;
`transient` — a server or network failure (overloaded, connection dropped
mid-response) that a retry has a real chance of fixing, and an omp turn that
ended `stop` with nothing in it — no text, no tool call, no image, at most
reasoning (omp's own `hasVisibleAssistantContent` test): the provider dropped
the reply, and omp retries only one that streamed nothing, so a reasoning-only
one (opencode-go-responses/muse-spark, mid-task) ends its loop as if done and
does not count as the route answering; `fatal` — a retry
cannot fix it (context too long, the model or subscription is gone,
authentication). All three read as plain `waiting` otherwise, so the
attention reason says which, the rail shows the reason instead of the
cut-off tail, and the session view offers Continue/Retry for the retryable
kinds (a plain send). The fleet auto-nudges the retryable ones through the
same guarded path as error screens — 5 minutes quiet first, one nudge across
the fleet at a time, three per spell, only while the error is fresh — and
never a fatal one. An error that names its own wait (`retryAfterMs`) backs
off up to it — 1, 2 and 5 minutes, then that wait — and is retried until it
clears, with no cap on tries: Codex's "Selected model is at capacity"
(`codex_error_info: "server_overloaded"`) is `transient` with a 10-minute
wait. The next prompt clears it. Rate limits stay on
`limitHit`, whose wait-out logic is theirs. An omp `session_exit` closes the
host's jobs and dialogs but does not advance the conversation's activity
clock: parking after retries are exhausted must retain the error reason,
without making that old error eligible for another automatic retry.

Whenever the fleet will tell a session to go on by itself — past a turn
error or an error screen, or after its 5-hour reset — the session carries
`autoResume: {at, attempt, of, after}` (`Fleet.autoResumeOf`, from the same
plan the nudges act on), and the board says when: the attention reason, the
session's error line or limit banner. Nothing waits on it: a message you send
first does the same job and calls it off. `after: "error"` — a turn error or
an error screen it will retry (`retrying` in `src/core/attention.ts`) — is not
your move: its attention is `running`, the board draws it as working (blue,
"Retrying"), and it is not pushed or reported as blocked or waiting (`agentbox
watch`, voice news) until the retries are spent. A nudge just sent still
counts for a minute, while it is typed and taken. An error screen is never
pushed, even with the retries spent (`blockedNews`, `src/core/push.ts`): the
board turns red, and the prompt that follows it is pushed as usual. A 5-hour reset (`after:
"reset"`) stays your turn.

Never copy credentials between homes. Both Claude and Codex rotate refresh
tokens; two homes holding the same refresh token means one of them is logged
out the next time the other refreshes. Every account gets its own login.

agentbox never refreshes a token itself. Usage reads that hit an expired token
report `stale` with the last good reading; the next CLI run on that account
refreshes it.

An account's email is re-read from its credential home every minute, so a
`/login` inside a home changes who the account is. Its label follows unless
you named it yourself; logged out, it has no email.

On macOS, a Claude subscription login held only in Keychain is checked with
`claude auth status --json` in that account's environment. Its reported
configuration directory must resolve to that account's home. This reads
identity only; usage stays stale when no readable usage token is available.
An unverified native login never makes a missing credential home eligible.

The rows in the `accounts` table are **credential homes**; an account is a
**login**. Two homes of one provider logged in as the same email are one
account: the dedicated home (or else the older) owns it, and the other is a
twin. `owners()` in `src/core/accounts/homes.ts` is the one place that is
resolved, and everything keys on it: the account list (`AppState.accounts`)
has one entry per login, with the other homes in its `alsoAt`; a session's
`accountId` is its home's owner; the balancer, claims, the attributor and
rate-limit hits all count per account. A session stays pinned to its *home* —
that is where its transcript is and what resumes it — and moving it between
two homes of one account is never offered, since it would cost a cold start
and change nothing about the limits. No view re-derives any of this.

That makes the default home **your CLI login**, not a subscription: every
subscription gets its own home, and the default home is a twin of whichever
one the plain CLI is logged into, so re-logging the CLI never takes an account
away from agentbox. Sessions you start from the CLI stay in the default home
and belong to its owner. The default home cannot be forgotten — it is
re-registered at the next start, and CLI sessions live in it. A default home
logged into an account no dedicated home has is an account of its own, and the
Accounts page offers to give agentbox its own login for it. Two *dedicated*
homes on one login are a mistake the page flags until one is logged into
someone else or forgotten. An account with no
login (mid-login, or logged out) is never placed on.

### Login

Driven from the web UI; the CLI runs in a PTY and the URL/code it prints is
shown to you. A login is done when the CLI exits 0 *and* its credential file
is there.

- claude: `CLAUDE_CONFIG_DIR=<home> claude auth login --claudeai`; show the
  URL, accept a pasted `code#state`.
- codex: `CODEX_HOME=<home> codex login --device-auth`; show the verification
  URL and one-time code.
- devin: `XDG_DATA_HOME=<home> XDG_CONFIG_HOME=<home>/config devin auth login
  --force-manual-token-flow`; show the URL, accept the pasted token.
- omp (OpenCode Go): `agentbox go-login <home>`, agentbox's own run of the
  OpenCode Console device flow (`src/core/accounts/godevice.ts`): show the
  link and the code, wait for the approval, keep the tokens with the email
  and workspace they are for. Two accounts signed in as one email are twins,
  as for every provider. Importing a home is refused with a 400.

Codex uses a fixed localhost callback port, so logins run one at a time per
provider.

### Usage

Each account publishes a list of windows:

    { id, kind: "short" | "weekly" | "daily" | "monthly", label,
      usedPct, resetsAt, windowMs, scope?: { model } }

- claude: `GET https://api.anthropic.com/api/oauth/usage` with
  `anthropic-beta: oauth-2025-04-20` (every 3 min per account, backing off on
  429), plus the free `cachedUsageUtilization` in each home's `.claude.json`
  whenever it changes. `five_hour` → short, `seven_day` → weekly,
  `limits[kind=weekly_scoped]` → weekly with a model scope.
- codex: `rate_limits` on `token_count` events in rollouts (free, as fresh as
  the last turn), plus `GET https://chatgpt.com/backend-api/wham/usage` for
  accounts with nothing running. Weekly only since August 2026, but the code
  takes whatever windows it is given. The same body carries
  `rate_limit_reset_credits`; when the count is above zero the client also
  asks `GET https://chatgpt.com/backend-api/wham/rate-limit-reset-credits` for
  the credits themselves, so the Accounts page can name each one and say when
  it expires.
- devin: best effort from `GetUserStatus`; absent is shown as unknown.
- omp (OpenCode Go): Go's own usage report, every 3 min:
  `GET https://opencode.ai/inference/go/v1/usage` with the account's Console
  token and `x-opencode-org-id`. It answers
  `{usage: {rolling, weekly, monthly: {status, percent, resetsAt}}}`: whole
  percent of the plan's dollar limits over 5 hours (short), the week to Monday
  00:00 UTC (weekly) and the subscription's month (monthly). Asked through the
  bridge (`/go/<account>/v1/usage`), which holds the credentials and refreshes
  a sign-in, so an idle account stays signed in. The count is the
  subscription's, whoever spent it: two accounts on one subscription read the
  same.

Readings are written to `usage_samples`, the raw material for calibration:
a row when a window's value or reset moves, and otherwise at most hourly.

Codex also grants free **usage-limit resets** — "Full reset" in the CLI's own
`/usage` menu — that clear an account's spent windows at once. agentbox reads
how many are left with the account's usage and shows them on its Accounts
card; **Use reset** spends one (`POST /api/accounts/:id/reset`, body
`{ creditId? }`), which calls
`POST /wham/rate-limit-reset-credits/consume` with a fresh `redeem_request_id`
(a retry cannot spend two) and then reads the account again, so sessions
stopped at that account's limit are told to carry on exactly as a window's own
reset does (`Fleet.limitEnd`). It never spends one on its own, and it asks
first. The button is offered whenever `available_count` is above zero: the
usage body's `applicable_available_count` says only that the provider thinks
nothing needs resetting right now, and a credit can be spent ahead of that
(observed), so it is shown as a note, not a gate.

The new-session prompt selects its project from registered repository names,
GitHub slugs and previously used folders, case-insensitively on whole names.
A full path or slug wins over a name inside it; multiple project matches leave
Where unchanged and ask you to choose. Picking Where manually holds that choice
until the prompt is cleared. The selected repository's worktree default and PR
references in the prompt still apply, including for scheduled sessions.

## Placing a new session (the balancer)

`src/core/balancer.ts` is a pure function from account state to a choice, with
the full reasoning attached. Everything is in **weekly percentage points**.

Inputs per account: weekly used `W` and reset, short-window used `F` and reset
(claude), and the outstanding claims of its active sessions.

- A session **claims** weekly points when it is placed or woken: what
  stretches of work on its model have gone on to use here from their start
  (`Forecaster.claim`) — the mean over the provider's sessions of that model
  family, a placed session's first stretch and a wake counted apart (a wake
  uses about a fifth of a first stretch), at the price of the provider's
  median account. Where fewer than 20 such stretches have run it is the
  model's listed claim (`listedClaim`, `src/core/claim.ts`) — Fable 3, Astra
  2.5, Opus 1.2, Sol 1, Sonnet 0.8, and the small ones (Luna, Haiku,
  GLM-Flash) 0.4, times the effort level (low ½, high 1, max 2; devin bakes
  the level into the model id): Opus is what was measured here and the rest
  keep their ratio to it, so a model listed as heavy is not taken for an
  average one before it has run. A model the table does not know claims the
  provider's mean, and with no history at all `claimNormal` (1.5).
  Consumption is the account's observed
  weekly increase apportioned across its active sessions by token-weighted
  cost. A claim lapses when the session's cache goes cold (`cacheWarmUntil`).
- What a session still holds — its **outstanding** claim — is a forecast once
  it has spent anything (`src/core/forecast.ts`): the average of what past
  sessions went on to spend from where it stands, by two things it shows —
  cost-equivalent spent in the last ten minutes (none: it is winding down, and
  holds next to nothing) and so far this stretch of work (a run of token
  samples with no gap over an hour). The table is fitted daily per provider
  from `token_samples`, and turned into weekly points by what the account's
  points have cost over the last two weeks (`attributions` over the same
  sessions' cost-equivalent). The model, the stretch's age, idle time and the
  spend of the last half hour and hour add nothing to those two. Until a
  session has spent anything, or where there is no history or no price, it
  holds `max(0, claim − consumedSoFar)`. `ClaimView.basis` says which, and
  the Calibration page shows the table.
- Effective weekly `W' = W + Σ outstanding`. Effective short `F' = F + Σ
  outstanding × 100 / shortWindowInWeekly` (24: one full 5-hour window is about
  24 weekly points), because the next hour of a session lands in the current
  short window.
- **Pace**: how fast the short window is really filling, from its readings
  over the last ~45 minutes (`usage_samples`; at least 10 minutes of them).
  Claims only count what the balancer placed; the pace also sees a lead's
  teammates, a session run by hand, one bigger than its claim. So with a pace,
  `F'` is a forecast: `F + pace × hours to reset`, plus the claims the pace has
  not seen yet — each outstanding claim times the share of the pace's span
  that had passed before its session was here to spend (started, or woken onto
  the account). A session started ten minutes into a 45-minute span counts
  about ¾ of its claim; one running since before the span counts none, since
  its spending is in the pace already. Without a pace, `F'` is `F` plus every
  claim. (The wake time lives in memory: a restart counts a session woken just
  before it as measured.) The new-session dialog and the Accounts page hatch
  `F'` on the 5-hour bar, so what they show is this forecast. Teammates and other sessions started by another one carry no claim of their
  own: their parent's covers them, and the pace shows what they really spend.
- **Gate**: an account can take a new session while `W' < 100` (and, for a
  model with a scoped weekly limit, that scope's `W' < 100`), while it is not
  actually at its short-window limit (`F ≥ 100` with no reset within
  `resetHorizonMin`), and while its pace would not run the short window out
  more than 10 minutes before it resets: a session there stops mid-work.
- **Rank** (claude): first, whether it has room in its short window for this
  session's claim (`claim × 100 / shortWindowInWeekly`: 5 for a claim of 1.2
  points). Room is short-window leg room `100 − F'`,
  raised toward 100 as the short window's reset approaches within
  `resetHorizonMin` (60). The weekly is no part of it: an account with any
  weekly left (`W' < 100`, the gate) takes a session whatever that session
  claims, so its last points are used rather than left for want of a claim
  that fits; with that claim on it `W' ≥ 100` and it takes no other. The
  session that runs it out is moved on (below). And the window must stay under
  its **load line** with the session in it: `shortLoadPct` (50) of the window
  forecast full, the other half being the margin for sessions that turn out
  bigger than forecast. An account that could not get through its weekly at
  that rate before it resets is loaded as far as it needs
  (`weekly left per hour × 5 h × 100 / shortWindowInWeekly`), up to 90.
  Among the accounts with room, the one whose weekly resets soonest wins, then
  the most weekly left per hour: the weekly is a budget lost at the reset, so
  what expires first is spent first — an account 7 points short of its limit
  with a day and a half to go takes every new session until those are claimed
  or its 5-hour window reaches the line, and then the next account to reset
  does. (Ranking by weekly left per hour alone spread work by need, which
  leaves every account a little short whenever there is less work than budget;
  the one about to reset loses its share for good.) A weekly that has not
  started loses nothing by waiting and goes last. Among those without room,
  the most room (the least overrun) goes first.
- **Rank** (weekly only, codex): soonest weekly reset, then most weekly left
  per hour.
- **Overflow**: nothing passes the gate, but some enabled account still has
  real weekly left (`W < 100`) and is not at its short-window limit. Claims are estimates, so rather than leave
  work undone, place on the least-claimed of those (lowest `W'`, then most
  room), as `mode: "overflow"`, and say so.
- Nothing at all: every account is at its weekly or short-window limit, or
  turned off. Say so,
  and let a manual pick override.

Two more things rule an account out, each said as its reason. A window
longer than the week that is spent and has not reset (OpenCode Go's monthly):
its week can read 0% and nothing placed there runs. And a refusal for want of
funds ("402 … Insufficient account funds", read from the account's recorded
limit stops): for 12 hours after the last one, since no window says when a
balance comes back. Before these an unfunded account with an empty week was
the balancer's first pick, and every session placed on it died on its first
call.

And a model the provider is refusing (`src/core/refusals.ts`). A caller names
the model and the balancer picks the account, so an account's usage says
nothing when the provider turns the model itself down ("Model is
unavailable"), or turns it down for one account ("This Go model requires
Global regions"): every call answers 4xx and a session placed there dies on
its first turn. What knows is the sessions already there. Each transcript
says what the provider last did with its model (`TranscriptFacts.modelOutcome`,
omp and opencode): when a call last answered, and the refusal standing since,
which is a 4xx that is about neither the request (too long, malformed) nor a
limit or an empty balance, and which only an answer clears. The fleet stores
it with the account it was earned on, since a session can wake on another. A
model on an account is refused while two or more sessions of the last day
stand refused there and no session still getting answers has had one since;
one refused session may be its own doing. An hour after the last refusal it
is tried again, one session at a time: until that one hears (ten minutes at
most) the route stays shut; answered, it is open; refused, it is shut for
another hour. Each account is judged on its own sessions, because a
transcript cannot tell one account's refusal from the model being down. An
account nothing has run the model on is tried, unless two or more accounts
are refused and none is getting answers: that is the model. A refused account is out
whoever meters the model, and overflow does not go there. Refused on every
account, the session is not started (409) and the reason names the model, the
refusal and when it is tried again, so the caller can start it on another
model; an account picked by hand still goes. A session started without a
model is judged on the CLI's own default (`ProviderAdapter.defaultModel`,
omp's `modelRoles.default`). This is learned, not listed: there is no table
of bad models to keep.

Worked example: A is at 13% weekly with four days left but its 5-hour window
is filling at 29%/h and would run out 20 minutes before it resets; B is at 14%
weekly, four days left, 30% of its 5-hour, filling at 7%/h with an hour to its
reset; C is at 49%, six days left, 5-hour fresh. A is out (pace). B and C both
have room for a normal session — B's window is forecast 37% full, under its
line with the 5 of a session claiming 1.2 points — and B's weekly resets
first, so B takes it, though C has more 5-hour room. Three sessions on, B is
past its line and C takes the next.

A session that stops at its account's limit — 5-hour or weekly — is moved
once in its life (`Fleet.continueStalled`) to the balancer's first choice
among the other accounts that can take a session and have weekly room for
what it claims (`elsewhere`; a new session may take an account's last points
because it can be moved on, and this one cannot be again — without that room
anywhere, the account with the most weekly left), and told to carry on there: the balancer runs accounts to their last point on purpose, so
the session that finds the end of one should not pay for it. Once
(`sessions.hopped_at`), so that a runaway session cannot run through every
account: the second limit it meets stops it, while each other session cut
off with it still has its own move. They go one at a time, each placed
knowing the one before. A session that has had its move, or has nowhere to
go, carries on where it is: a minute after its limit lifts it is told to go
on, on the same account, when that comes within five hours of the hit (a
5-hour window's reset always does). A weekly limit that runs its days out is
left to you (the limit banner). An error nudge never moves a session.

Whether a limit still stands is the account's usage to say, not the session's
memory of the message (`Fleet.limitEnd`). While a window of the account is
spent, the limit ends at that window's reset. Once none is, and one was as
the hit struck (`usage_samples`), the limit has lifted, whatever lifted it —
the window's reset, a reset redeemed at the provider, a bigger plan — and the
session has no `limitHit`: it takes messages, is no longer the fleet's to
move, and is told to carry on as above. The time the message names counts
only for a hit no window ever accounted for (a rate limit, an empty balance,
an account whose usage cannot be read). A parked or stopped session's
`limitHit` follows its account's usage the same way.

A turn that dies mid-flight is the other way a session stalls: the CLI stays
up with the error on screen ("Send a message to retry") and the transcript
never closes the turn, so the board would call it working forever. A turn open
but silent for two hours reads waiting instead (`STALE_TURN_MS`, the judgment
recovery already makes); a devin session showing the retry error at the foot
of its screen reads `blocked` — rate limit, or error — and
`Fleet.nudgeErrored` tells it to go on once the error's reset window has
passed: one nudge across the fleet at a time (several sessions retaking one
rate-limited account in lockstep is what stuck them in the first place), three
per spell, then it is yours. An error that names its reset — devin's "Reached
free model rate limit … Your limit will reset in 1 hour 17 minutes" — is left
until then and nudged once it has passed, however long that is, with no cap on
tries: every retry before it is refused the same way, after a round of devin's
own retries (`statedWaitMs`, `src/core/retrywait.ts`). The wait counts from
the hit devin logged (`limitHit`) when there is one, else from when the fleet
first read that error off the screen. A nudge types where the session is,
however cold.

Every placement writes an `assignments` row holding every candidate as the
balancer saw it (weekly and short used, resets, summed outstanding claims, the
derived room and gate), the settings in force, the mode and the reason. That
is enough to see why each placement went where it did, and to replay the
ranking against other settings; it is not the raw windows or the per-session
claims, so a replay that changes how claims are apportioned needs the
`usage_samples` and `token_samples` of the same week.

### Calibration

`src/core/calibration.ts` reads the metrics tables and proposes settings:

- `shortWindowInWeekly`: regression of weekly increase on short-window
  increase over intervals where neither window reset.
- `claimNormal`: the distribution (median, p75, p90) of what sessions
  actually consumed. With claims scaled by model (`src/core/claim.ts`), it is
  the fallback for models the table does not know, not every session's number.
- how often a placement was followed by a rate-limit hit on that account.

## Superagents

A superagent is a program that runs on agentbox, not in it: Steward, Jupiter
and Vulcan in `superagents/` are examples, and anyone's coding agent writes
more. [docs/superagents.md](superagents.md) is its contract. Agentbox's part
is small and knows no superagent by name (`src/core/superagents.ts`):

- **The registry.** `agentbox superagent add <dir>` reads the directory's
  `superagent.json` into the `superagents` table: a name, where its code is,
  its main conversation. The manifest, code and state stay the superagent's.
- **Its program.** With `run`, the server starts it in its directory and
  starts it again when it exits (backoff doubling to a minute; at once after
  a minute up), giving it its port, a token, a home of its own and the API's
  address. A crashed server's leftover program is stopped first (`reap`), so
  two never run.
- **Its main conversation.** The Agents page shows it as the superagent's
  chat with the Sessions page's own pane: a same-session schedule's session
  (`main.schedule`), the session the program named, or one agentbox starts
  from `main.start` on the first message (`POST /api/superagents/:name/chat`,
  idempotent by its send id). It follows handovers (`Fleet.heir`).
- **Its page.** Agentbox relays `GET /agentbox/view` and `POST
  /agentbox/action` to the program with its token, and draws the blocks it
  answers with; an action carries who asked (`caller`: an authenticated
  session, and whether a browser sent it).

The parts of the API it leans on that are new with it are generic: a session
started `readOnly` (Codex's sandbox, kept across resume), a session or a
card with `notify: false`, and `POST /api/sessions/:id/handover`.

## Master session

`agentbox mcp` is an MCP server for one conductor session with a compact view
of the whole fleet: `fleet` (every session, plus each account's usage),
`read_session`, `send`, `spawn`, `resume`, `interrupt`, `close`. It is a
thin client of the HTTP API and needs the server running. The conductor is an
ordinary claude session started from the UI with that server attached;
nothing about it is special to the rest of the app.

## Models devin does not sell (the devin bridge)

A devin session can run on a model from another provider, in devin's own
harness: `src/bridge/` is a local server that stands in front of devin's API
server, adds the model to devin's catalog with its own context window and
compaction thresholds, and answers that model's requests from its provider.
Such a session is an ordinary devin session to everything else here — same
transcripts, same tmux, same resume — started from the same picker; the
adapter points it at the bridge (`WINDSURF_API_SERVER_URL`), the balancer
places it without counting it against the devin account (`unmetered`), and
the bridge runs as its own systemd unit so a server restart does not touch
it. The same bridge serves OpenCode Go to omp and opencode sessions on a
given account's credential (`/go/<account>/…`, see Accounts). [`docs/devin-bridge.md`](devin-bridge.md) has the design, the operating
notes, and the walkthrough for repairing it when a devin update changes the
wire format.

## Subagent MCP

`agentbox subagent-mcp` is a separate MCP server, for any agent that wants to
delegate: `agent`, `send_message`, `collect`, `list_agents`, `transcript`,
`interrupt`, `stop_agent`, `workflow`. Each agent is an ACP process — `omp
acp` by default, `devin acp` when the caller passes `provider: "devin"` —
owned by the MCP server, run in the caller's working directory (or `cwd`) and
blocked on like a function call; `workflow` runs a script that fans many out.
For independent tasks, use one `workflow` with `parallel`: clients such as
Devin serialize separate blocking `agent` calls. Workflows default to six
concurrent agents; callers can set `concurrency` up to the total-agent bound
(200), including one slot per task when the whole batch should run together.
It needs neither the agentbox server nor the database, and its agents die with
it — but not for good. Every process agentbox starts has `AGENTBOX_SESSION`
set to its session id (and a claude has `CLAUDE_CODE_SESSION_NAME` too, so
other Claude sessions message it by that id rather than its folder's), which the MCP inherits and writes into each agent's
`meta.json` as `session`. When that session runs again, its new MCP brings
back, parked under the same names, the agents its last run left unfinished:
cut off mid-turn, or holding answers nobody collected (restored to their
mailboxes from the record). The next `send_message` resumes each one's own
conversation with its own system prompt, model and permissions, as after an
idle park; every tool result says which are back until each is spoken to or
stopped. An MCP shut down with its client records why (`CALLER_GONE`,
distinct from a caller's `stop_agent`), so a finished agent stays finished. omp runs `AGENTBOX_SUBAGENT_OMP_MODEL`, else
`opencode-go-responses/muse-spark-1.3-contributor`; devin runs
`AGENTBOX_SUBAGENT_DEVIN_MODEL`, else its own configured default.

The CLIs differ in two ways the pool hides (`src/subagents/backend.ts`). omp
takes the subagent contract as `--append-system-prompt`; devin has no such
flag, so the contract leads the first message of the conversation. A
read-only omp agent is started with `--tools` naming only tools that cannot
write (omp asks permission before a shell command but never before an edit);
a read-only devin agent is put in its `ask` mode, which has no write or shell
tools, and a devin writer in `bypass`.

It keeps its data under `$AGENTBOX_HOME`:

- `subagents/<pid>-<n>-<name>/` — one per spawn: `system.md` (the subagent
  contract it was given), `meta.json` (identity, the CLI, the brief, and the
  CLI's session id), `state.json` (a snapshot refreshed every 2s) and `transcript.jsonl`
  (the event log). Pruned after 7 days.
- `live/*.live` — one pre-rendered status line per agent that is running or
  holding an uncollected answer, and per workflow:
  `<unix s>\t<cwd>\t<owner>\t<text>`, read by a status-line script.

Each CLI keeps an agent's own transcript in its default store (omp runs
without `--session-dir`), beside every other session of that CLI. The fleet
tells a pool agent by its `meta.json` `provider` and `sessionId`
(`poolAgents` in `src/subagents/record.ts`) and shows it as a child of the
session its `owner` names, folded under it, titled with the agent's name.
While its MCP server lives, its `host` is `subagent`: read-only, because the
server holds the conversation open and would take a stop, an adopt or a typed
message for a crash, so the API refuses those and points at the parent.
Its status and `subagent.answerWaiting` (a finished turn its caller has not
collected) come from the server's `state.json`, which knows before the
transcript does. Stopping or closing the parent stops them all, and the UI
says which before it does. Once stopped, a pool agent is an ordinary stopped
session and can be resumed in agentbox's tmux; it stays listed only while its
parent's process runs, and is shown closed after that, so an old fan-out
neither lands at the root of the board nor piles up under a stopped parent. Code: `src/mcp/subagent.ts` over `src/subagents/`.

Who agentbox works for is the machine's business, not the repo's: `agentbox
onboard` (and the server's boot, when the file is missing) derives a name,
email, GitHub login and timezone from git, `gh` and the passwd entry, and
writes what it finds to `<agentbox home>/user.env`. The file wins over
derivation; re-onboarding fills only keys still missing, so a hand-written
`USER_CONTEXT` — the line the voice agent knows its human by — survives. The
voice prompt and the Deepgram keyterm bias are built from this file and the
tracked repos' names; nothing personal is hardcoded anywhere.

Setup is one checklist, computed by probes and rendered the same everywhere —
the board's first-run card, `agentbox onboard` and `doctor` all read
`onboardingItems` (`src/core/onboarding.ts`), so no two views of "what is
missing" can disagree. Its inventory: tmux and git; gh authenticated;
an account *logged in* (registered is not logged in — the auth state is what
counts); voice keys; the systemd unit; lingering, without which the unit
starts at first login rather than boot; the board installed as an app. A
feature that needs setting up adds an item there the same way it adds a
dependency check. The card also offers to adopt sessions already running in
your own terminals — they are on the board the moment the fleet's first tick
sees them, but adopting one stops its process and resumes it inside
agentbox's tmux, so it is offered one at a time through the guarded adopt
path, never done on its own. `bun scripts/fresh-machine.ts` rehearses all of
it on a throwaway HOME; that rehearsal is how a setup claim is known to hold.

## Global MCP servers

The MCPs page keeps one list of MCP servers that every agent agentbox starts
or resumes is given, on every account (`src/core/mcp.ts`). The list is
agentbox's: `<agentbox home>/mcp/servers.json`, 0600 in a 0700 directory,
with no backup copy (one would keep a rotated token on disk). A server is a command
(stdio: command, arguments, environment) or a Streamable HTTP URL with
headers. Env and header values are the user's secrets: they leave the server
only in the files and environment handed to the CLIs, never in an HTTP
response, and an edit that names a variable without a value keeps the saved
one. A value that looks like a substitution (`${VAR}`, `{env:…}`,
`{file:…}`) is refused, because each CLI would read it differently.

agentbox never edits a CLI's own config to pass the list. Each launch resolves
its account, working directory, profile, explicit flags and environment
(`withGlobalMcp` in `src/core/mcp-reach.ts`). The layer uses private snapshots
under `<agentbox home>/mcp/`; an existing session's snapshot never changes.
With no server enabled, a launch is exactly what it was without the feature:
no flags, no variables, no rewritten config. When the list changes, snapshots
that no process of ours names in its argv or environment (and that no launch
used in the last ten minutes) are deleted, so a removed token does not stay
on disk; the page's view reads configs but writes nothing.

| CLI | how a session gets the list |
|---|---|
| claude | `--mcp-config <snapshot>` combined with its explicit MCP files |
| codex | per-server `-c mcp_servers.<name>=…` overrides; keeps the selected or default profile |
| opencode | MCP entries merged into `OPENCODE_CONFIG_CONTENT`; keeps explicit files, adopted config and the account's bridge settings |
| muse | per-server `-c mcpServers.<name>=…`; secret values referenced through the session's environment |
| devin | a generated `XDG_CONFIG_HOME` with an MCP file containing globals plus native user entries; all other config entries link to their original locations, and the data/auth home stays put |
| omp | `--extension <snapshot directory>`, adding an MCP extension alongside native settings and the active profile |

A native name, including a disabled entry, is kept. Account, project, profile
and explicit definitions are checked at launch; global defaults on the page
are not a prediction of every project's settings. Discovery reads Devin's
user and project MCP files and omp's native files as well as Claude, Codex,
OpenCode and Muse settings. Native plugins and organization policies remain
under their CLI's control. OAuth logins stay with the client that made them;
unsupported import shapes are shown with a reason. Project imports require
an explicit promotion. Turning off a global entry leaves an independently
enabled native definition available, and the page says so.

`mcp-proxy.ts` forwards MCP over stdio to either a local command or Streamable
HTTP. omp uses it because its native config interprets bare variable names
and `!command` values; the proxy preserves literal values, including empty
strings, and the session cwd. Codex uses it for definitions containing env or
header values, or a URL with a query string, so those values never appear in
argv; Muse uses it for such a URL too. Its config flags contain only a private
snapshot path. Variables that hold values (Muse's `AGENTBOX_MCP_<n>`,
opencode's `OPENCODE_CONFIG_CONTENT` with the layer in it) are marked secret
(`Command.secret`) and exported by tmux's private, self-deleting launcher
script rather than put on the command line tmux runs. The proxy runs on the installed Bun and MCP SDK,
without downloading a package at session startup.

The ACP pool resolves stdio commands to absolute executables. HTTP is passed
directly when advertised, otherwise through the same stdio proxy. Resume is
tried first when advertised (or when nothing is), and load after it when
resume is not implemented, as before the list existed. A server whose command
is missing is left out; if the list cannot be read, or the agent refuses a
session with it, the session opens without the global servers. Each is logged.

The global layer never stops an agent from starting. A server whose command is
not on the session's PATH is left out and the rest are given; a broken
registry, a native config that does not parse, a layer that cannot be written,
an explicit whole-map Codex/Muse override (`-c mcp_servers=…`, which would
erase the global entries) or omp's exclusive `--trusted-extension` launches the
session without the layer. Either is logged, recorded in the session's
`AGENTBOX_MCP_STATE` (`skipped`, `error`) and shown on the MCPs page. Adopt,
account moves and the devin permission repair build their launch before
stopping the old process.

Launch metadata records only the names handed to a session and native conflicts
for the page. Separate private environment metadata identifies the precise
managed arguments and original environment to restore during adopt/recovery;
managed flags and variables are removed before the next layer is generated.
Updating, disabling or deleting a server therefore cannot accumulate stale
arguments on resume. User profiles and unrelated overrides remain intact.

The page distinguishes supported launch integration, configuration problems,
native availability, launch snapshots and sessions that need a later start or
resume. A configured or passed server is not a successful connection: runtime
connection failures and client policies are reported inside that agent. An
older process with no launch metadata is marked unknown. Changing the list
restarts nothing. Check starts the selected server, lists its tools, and stops
it, on request only; discovery never runs a found definition.

## The shared cloud (optional)

A team that runs agentbox on several machines can share one Supabase project:
people and their sign-ins, workspaces and invites, registered machines and
their scopes, plans and skills with revisions, and messages between agents on
different machines, with receipts. Each machine keeps its agents, transcripts
and provider credentials, and only calls out. Without `cloud.env` none of it
runs. [docs/cloud.md](cloud.md) is its contract: the model, the security
rules, the API (the database RPCs and `/api/cloud/*`) and the setup.

## Shared Agents

The Agents page is a workspace directory of actual persistent instances, above
Sessions. A shared/team instance separates its creator/maintainers, accountable
human on each work item, execution installation and GitHub actor. Its identity
survives session replacement or host changes. Standalone Sessions retain their
existing privacy. [docs/agents.md](agents.md) describes setup and the contract.

`src/cloud/agents.ts` owns safe shared record schemas; `agent-client.ts` exposes
human and installation RPCs. New Supabase migrations enforce workspace reads,
maintainer edits, independently granted execution hosts, globally deduplicated
workspace work, fenced run leases, explicit handoff and immutable action approval.
Expiry leaves a run uncertain and exclusive until the host proves its writer
stopped. Release scope additionally excludes concurrent work on the same real
repository/environment.

`src/core/agents/runtime.ts` is a Scheduler-driven reconciler around Fleet, not a
second session runtime. Its local SQLite journal holds execution bindings,
intake, side-effect attempts and session references only. Fleet remains the owner
of process/session behavior and provider transcripts remain the conversation
record. Only safe work/progress, host/freshness, evidence and session references
are shared. A remote reference never opens a remote terminal.

The GitHub App broker holds scoped installation tokens in the server. Named bots
use verified App identities and mapped bot author emails. Human-controlled
outreach preferences bind to OAuth-managed GitHub identities, never editable
expertise profiles. Every outbound targeted action rechecks consent, identity,
policy and current ownership. Missing or revoked consent surfaces needs-human;
shared sessions cannot use cloud messaging or push notifications as a workaround.
Messages between local sessions are not outreach: any local agent can send one,
under the send guard of [Messages between sessions](#messages-between-sessions).
Automatic and prepare-for-approval modes are explicit, and an interrupted action
is uncertain rather than replayed. Cloud delivery grants remain independent.
## Projects (the board's switcher)

A project is one registered `Repo`. The sidebar's logo names the selected
one ("All projects" with none) and opens the switcher; Sessions (the rail,
its bookmarks, its closed list), Review, the nav badges and the new-session
dialog's defaults follow it, while accounts, credentials, MCPs, system status
and machine settings stay global.

The selection is part of the URL: `#/route?project=<repo id>` (an empty
value is an explicit "All projects"), with `workspace=<id>` beside it for the
Team page's cloud workspace, so Back, a reload and separate tabs each keep
their own context (`scopeOf`, `selectScope` in `web/src/route.ts`). An
unscoped link to a list page takes the last scope this browser used
(`localStorage` `agentbox.navigationScope`, `restoreScope`); a link straight
to a session stays unscoped and is scoped to that session's project once it
is known. Every internal link carries the current scope (`hrefOf`), and a
link that carries another one is a plain hash navigation into it.

A session's project is its checkout: `Repo.checkoutRoot` in state is the
repo's canonical, symlink-resolved checkout path (a GitHub clone's under the
repo root), and the session whose `repoRoot` — a worktree's is its main
checkout — is that root, or a session with no repo root under it, belongs to
the longest such root, so a nested repository beats its parent
(`src/core/projects.ts` `sessionProject`; a caller may pass explicit
bindings, which win). A Review card belongs to the repo of its PR's slug,
else to its session's project. What matches no repo appears only under All
projects. `GET /api/sessions/closed?project=` filters before paging.

Selecting a project is navigation only: it starts, stops and rebinds nothing
and changes no account. A session opened under another project's scope says
so and offers to open in its own; a removed repo's scope says the project is
no longer registered and offers All projects.

## Security

PR transfers require the holder's private session capability in
`x-agentbox-session` and `x-agentbox-session-token`. A process ID is a routing
hint, never authentication. The CLI reads its capability from a private 0600
host file; it is never exposed through state or transcript APIs. This does not
isolate processes with deliberate access to the same Unix user's private files.

The server binds loopback and requires, on every mutating request, an
`x-agentbox: 1` header plus an Origin (when present) and Host that are
loopback. That blocks a web page in your browser from driving the API, which
v1 allowed. Skill paths are confined to the skill roots by realpath; skill
names are validated as a single path segment.

WebSockets:

- `/ws` — server pushes `hot`, `cold`, `metrics`, `error`, and `timeline` for
  the one session the client `watch`es. `hot` (the open sessions) and `cold`
  are whole on connect; after that `hotDelta` carries only the open sessions
  that changed, each whole, and the ids no longer open, and `coldDelta` only
  the parts of cold state that changed. Closed sessions are not pushed: the
  See closed list pages them from `/api/sessions/closed`, and `closedStamp`
  moves when one is closed or reopened (`{"type":"watch","sessionId":…}`;
  `null` stops). The first timeline frame is `reset: true` with the newest
  page and a `before` cursor for paging back; then increments, each with the
  `cursor` to resume from. A tool event may be re-sent with the same id when
  its result arrives — replace by id; the re-sent event carries `endedAt`, the
  moment the result was written, so the UI can show how long the call took. With it, `btw`: the watched session's
  side questions, all of them (`items`), on watch and on every change. The client may also send
  `{"type":"ping"}`. `build` (`{"type":"build","entry":"index-….js"}`, on
  connect and after each `web:build`) names the UI build on disk; a page
  loaded from another reloads automatically after two seconds without interaction,
  including in the foreground (`web/src/lib/update.ts`). Drafts, attachments,
  edited forms, in-flight actions, dialogs, recording, voice and terminal views
  defer the update; it retries until safe without requiring navigation or approval.
  The server listens from its first second, before its first pass over the
  transcripts is done: until then a page's socket gets `starting`
  (`{"type":"starting","read":N,"of":M}`, on connect and every half second)
  and nothing else, a watch sent meanwhile is answered once the board is
  ready, every `/api/*` request but `/api/health` waits for that too, and
  terminal and voice sockets are refused with a 503. Just before it exits
  (SIGTERM, a restart) it sends `restarting` to every page and closes with
  code 1012; the page then retries every half second rather than backing off.
- `/ws/term/:id?cols=&rows=` — a live terminal on the session's tmux. Server →
  client: binary frames of raw terminal output; a session not in agentbox's
  tmux gets one text frame saying so and a close with code 4000. Client →
  server: text frames `{"type":"input","data":"…"}` and
  `{"type":"resize","cols":N,"rows":N}`. Closing the socket detaches; the
  agent keeps running.

### Agent conversations and recommendations

Local Agent chat shares Sessions' attachments and selected-session facts. The
paperclip's hover/focus picker shows the newest three screenshots from macOS's
configured screenshot folder (Desktop by default), or Pictures/Screenshots and
Desktop on Linux. Opening it reads metadata and raster previews only; selecting
one copies it through the ordinary image-upload path and leaves it in the draft.
`GET /api/screenshots` returns opaque preview IDs, names and modification times;
`GET /api/screenshots/:id` serves only a recently listed, unchanged raster file.
Session capability headers are refused; neither endpoint accepts a client path.
Shared conversations do not attach this machine's local image paths.

A template can give its local instance a stated authority in the first prompt
(`LOCAL_AUTHORITY`); shared definitions are unchanged. Vulcan's lets it decide
whether an issue is a routine fix: it investigates, reproduces, prepares a fix
in an isolated worktree, commits it on its own branch and validates it without
asking. User authorization persists across steps: it asks through Review only
when a publication, outreach, a merge, integration into a checkout others edit, a deployment or service restart, a
destructive step, credentials access, or anything a stored preference or
repository rule reserves is not already authorized, with one request for the
remaining sequence. A conversation gets this when it starts or continues from a handoff.

Messages under four minutes apart show timestamps on the first and last message
of the group; carried-conversation boundaries start a new group. Recommendation
guidance is displayed as a quoted reply without its transport IDs. The original
provider text, copy action and exact approval scope remain intact.

Agent detail defaults to Chat, with Feed and Settings tabs. The header holds
only the avatar, name, role and status, and the tabs. Settings has the agent's
description and all its configuration: Local or Hosted, Enabled, provider,
repository, memory and picture. An old `#/agents/<agent>/about` link opens
Settings. Chat uses the Sessions
message rows, composer input and Send control. Submitting a message returns that
chat to the bottom immediately, before its delivery receipt; incoming replies
follow only while the reader is already at the bottom. A read page of the
viewed conversation's newest events carries `presence` (`presenceOf`), from its
transcript order and session facts, never a timer or a stored copy. The
person's newest message there shows Sent once recorded, and Read once the
agent wrote anything after it (reply, thinking or tool). An error or a turn
on something else is not read. A message that Claude holds mid-turn shows
Queued while it is in the session's queue. Three dots stand for the agent while
its turn is open, unless the fleet started that turn (a handoff request or a
keep-warm). Older and carried messages show no status. A creation card (`CreationDraft.at`)
and a recommendation card (`created_at`) sit in the chat at the time they were
proposed, like a message, and scroll with it; a draft from before drafts recorded
`at` shows last. Local agents can use
existing Fleet/provider accounts before shared cloud setup. A shared conversation
is a read-through of the agent's verified run/predecessor provider transcripts;
`src/core/agents/conversation.ts` owns that scoped read and delivery bridge.
`src/cloud/agent-conversation.ts` owns bounded encrypted live relay transport and
shared proposal schemas. Realtime Broadcast carries encrypted pages without a
cloud transcript copy. Membership and execution grants are checked per request.
`agent_proposals` stores agent-authored recommendations, and `agent_commands`
stores only pending input until its terminal receipt purges the body. Existing
managed action approval remains the authority for a proposal's concrete action.

A message you write in Agent chat (to the main conversation or to a writable
work session) interrupts a running Claude or Codex turn, as Escape does by
hand. `Fleet.endTurnFor` reads the board fresh, presses Escape, and types the
message after the session shows the turn ended (at most 8 seconds; after
that, the message goes in mid-turn as before). All request, ownership, pause
and receipt checks run first, and the attempt boundary comes after the
interrupt, so a failed interrupt leaves the message unsent. Fleet does not
press Escape when the turn is over, a dialog or question is up, Claude's
queue holds a message (Escape would put it back into the input box and send
it inside yours), or nothing was written since the newest prompt (the turn
has just started). In these cases the message goes in as before. Approvals,
guidance on a recommendation, checkpoints, fleet notes, agent-to-agent sends,
requests with a session capability, shared conversations and the Sessions
composer never interrupt. Muse and other providers get the message as before.
Escape also stops the turn's foreground tool, as it does by hand. The unit
tests use fake terminals, so `bun scripts/interrupt-smoke.ts` checks the real
CLIs: one Escape ends a running turn within the wait, the transcript records
it, and the next message starts a new turn. It records each passing CLI
version in `$AGENTBOX_HOME/smoke/interrupt.json`, and `agentbox doctor` warns
when an installed version has not passed; `--if-changed` suits a schedule.

The persistent shared Chat coordinator has its own capacity: opening Chat does
not occupy a configured repository-worker slot. Its broker rejects repository
actions; canonical intake creates separately claimed work under the existing
activation policy. Current members can begin/give guidance to an enabled shared
conversation without becoming agent maintainers. Feed approvals persist their
delivery identity before dispatch and show queued, delivered, refused or uncertain
outcomes; uncertain requests never replay automatically. Local idle provider/repo
changes prove and retain the previous transcript reference before stopping its
process and starting fresh, without moving warm sessions between accounts.

### Agent memory and conversation rollover

`src/core/agents/memory.ts` keeps bounded, typed records per agent instance in
the private runtime journal: handoffs (`{intent, decisions:[{decision,why}],
open, commitments, refs:[{label,ref}]}`, at most about 500 words), decisions
recorded during work, and durable preferences (at most 40, 400 characters
each). Each record names its source session; none copies a transcript, and
credential-shaped text is refused. Records are evidence for continuity, never
approval. A local agent's scope is its own ID; a shared agent's is
`shared:<agent UUID>` on its execution host only, never uploaded.

`AgentConversations` keeps one provider conversation while the user chats. The
Scheduler pass asks the current conversation for a handoff once the user has
been away `idleMin` (default 10) or the conversation is past `contextPct`
(default 60) of its context, while enough of `Session.cacheWarmUntil` remains to
write it: three minutes, or 40% of a shorter cache's life. A short cache is asked
sooner, at its lifetime less that lead and half a minute (a five-minute cache
after about two and a half idle minutes), so it too gets a handoff while warm.
A conversation that went cold without one continues as it is, and is asked the
next time it is warm and idle. The request is a fleet note
(`[agentbox: memory checkpoint <UUID>] …`), hidden from Chat. It and its reply
refresh the cache, so another request needs a real prompt in between: the
transcript tail decides, with keep-warm notes skipped. A request with no handoff
after 15 minutes fails and is not retried before new activity.

Fleet asks the conversations hook before `send` or `note` delivers anything to a
session. For an agent's current conversation that is cold (past
`cacheWarmUntil`) or past its context budget, at a turn boundary, with nothing a
stop would lose (`Fleet.stopHold`, the parking checks), and whose newest real
prompt is the checkpoint its saved handoff answers, the hook chooses where the
successor runs (below), journals the replacement with that choice, stops and
proves the old process gone, records the successor, and starts it with the agent instructions, preferences, the latest handoff, up to two
earlier related handoffs, decisions since, live current work (works, waits,
Review cards, PR claims, started sessions), the previous session ID and the
message. The successor is proven when its transcript exists (the CLI took the
prompt), within 60 seconds. Only then does `Fleet.handOver` move succession, and
Review cards and PR claims move; the old session is closed alone. A successor
that fails to start, or exits first, is stopped and proven gone, and the message
goes to the old conversation instead. The message is delivered once:
the receipt's attempt boundary is the successor's start. Messages queued for the
old ID go to the successor; resuming the old one is refused. A grant whose
requester is a replaced coordinator stays usable by its successor. A missing or
stale handoff, a running turn, or a hold sends the message to the old
conversation as before. An undone successor leaves the old one parked and the
checkpoint failed; a restart finishes a successor with a transcript and undoes
one without. A hook failure other than its own refusal never blocks ordinary
messages. Shared coordinators keep handoffs and
start new runs and human-authorized rotations from them; automatic shared
rollover is not done, because rotation needs the installation owner's token.

The bootstrap is assembled by whole lines within 12,000 characters: a handoff
too long for what is left loses its last lines (said, with how to read the
rest), and an earlier one that does not fit is left out. Only the handoffs
whose text went in are recorded as supplied.

**Agent files.** Each local agent has `SOUL.md` and `MEMORY.md` in its
private directory `<agentbox home>/agents/local/<agent id>/` (0700; files
0600), named as OpenClaw names them and, for `MEMORY.md`, as Muse Code does
(`src/core/agents/files.ts`). Nothing uploads them, and neither holds a
transcript or a credential. `SOUL.md` is the agent's persona, voice and
boundaries: Agentbox creates it once from a seed and never writes it again;
the user and the agent edit it, and the agent tells the user when it does.
Each fresh conversation (a first message or a rollover) reads it once, after
the definition and rules, which it never overrides: whole lines within 4,000
characters, a note for what was left out, one line for an untouched seed,
and nothing but a note when it holds credential-shaped text. `SOUL.md` wins
over a lowercase `soul.md`. The agent record keeps the SHA-256 of the
`SOUL.md` its current conversation started with (`files`), never the text,
so the Memory panel can say it changed. A warm conversation is never sent it
again. `MEMORY.md` is a read-only view of the journal: every active
preference, the latest 20 decisions and an index of the latest 20 handoffs,
within 20,000 characters. It is rebuilt after each handoff, note and
preference write and when a conversation starts, and is not put in a prompt
(the bootstrap carries the same facts). The journal stays the only writable
memory: a `MEMORY.md` that is not what Agentbox last wrote is renamed to
`MEMORY.edited-<time>.md`, reported in the Memory panel and to the next
conversation, and never used or imported. A file error never blocks a write
or a start. Shared agents have no files; their definition is their persona.

**Automatic provider.** A local agent's `provider` is the provider of its
current (or last) conversation; `pinned` is an explicit override, and its
absence is Automatic, including for every record written before this (the old
implicit Codex default is not a pin). Only a fresh start chooses: the first
message, or a rollover. A warm conversation keeps its provider and account
whatever another provider's headroom. `src/core/agents/providers.ts` decides:
the pinned provider alone, otherwise Claude and Codex; a provider whose CLI the
adapter's cached `detect()` does not find is out (placement does not check
that); the rest are asked of `Fleet.placement`, which applies the balancer to
that provider's own accounts, so logged-out, unfunded, refused and spent
accounts are out there; headroom ("auto"/"manual") ranks before "overflow".
Within a tier, the weekly left on the Codex account placement picked sets the
order: above 50%, Codex first; below 10%, Claude first; from 10% to 50%, a
conversation keeps Codex first and the agent's implementation (work writer)
sessions alternate, each one starting on the provider its last writer did not.
With that weekly unknown, the previous conversation's provider first, then
Claude, then Codex. A writer is chosen by the same rule when its work starts
(`AgentWork.writer` keeps the provider and why); a pinned agent's writers use
its pin. Percentages are never compared across providers. The provider, the account
placement picked, the model (the provider's configured default, or the CLI's
own) and the reason are journaled before anything stops, and the successor is
started on that account; a restart finishes on the journaled choice. With
nothing available, nothing is stopped and the old conversation keeps the
message; a first message is refused with the reasons. Settings shows Automatic,
the current provider and why; the creation card defaults to Automatic for local
agents. Shared agents run on their execution host's configured provider, so a
shared creation draft must name one.

**Sender attribution.** `sendAsAgent` records each send before typing it
(`src/core/senders.ts`: recipient, sending session, whether the sender was
authenticated by its session capability or the server's own runtime identity,
the registered agent that session belonged to then, and a digest of the body;
never the body) and puts the record's id in the mark:
`[via agentbox send from <session> #<record>]`. Timeline pages, the live
timeline stream and agent chat pages attach `sender` to each user-role event:
`agent` (a registered agent, with its current name and picture), `session`,
`system`, `schedule`, `cloud`, `peer` or `unverified`. An event is attributed
only when its mark names a record for this session (or one it took over from)
with the same sender and digest, written within a day of its arrival; a typed,
copied, edited, legacy or unauthenticated mark is `unverified` and takes no name
or picture from its text. The agent is resolved from durable records (an
agent's current and replaced conversations, its work families), so a closed or
replaced sender keeps its identity. Shared readers see `agent`/`session` without
local names. A registered agent's message shows as its bubble beside its
picture or icon; agentbox's notes and unverified marks stay quiet folded rows.
A session's opening prompt has no mark. When a session authenticated by its
capability starts another (`POST /api/sessions`), the spawn records that
prompt's digest (`recordOpening`); the child's unmarked message with that
digest, within two minutes of the record, is the starter's. A child the fleet
linked to a parent (not by hand) with no such record shows its opening as
`unverified`: not yours, and not named from its text. Later messages are yours.

**Message bar.** The Agents composer is one low rounded bar: a paperclip at its
left (local agents only: an image is uploaded here and sent as its path on this
machine, which another execution host could not read), `Message <agent>`, and
Send as a lighter rounded square at its right; it grows for more lines.

Main chat scrolls back past the start of a conversation started from memory
into exactly the conversations whose handoffs its first prompt carried
(`contexts[session]`, written with the rollover journal, so later handoffs or
relevance never change it), newest first, and no further. `ReadCursor.history`
names one of them; any other is refused. Their events come from their own
provider transcripts on demand, ids prefixed with the source session, with
`source` and `carried: {handoff, at, oldest}`; the UI mutes both sides of them,
divides conversations, and marks the oldest as the start of what was carried.
The composer and receipts stay bound to the current conversation, and nothing
shown is added to a prompt. A source that cannot be read returns an error and
the same cursor, to retry.

An agent's picture belongs to its record (`avatar: {file, at}`), under
`<agentbox home>/agents/avatars/` (0600), so it outlives every conversation.
Chat draws replies on the left with the picture (or the agent's own icon) and
name, and the viewer's own messages with their GitHub picture. A shared chat
has no sender identity for human messages, so it draws them without the
viewer's picture.

Main chat headings use the agent's name and at most ten words of its role,
independent of provider session titles. Navigation resolves the current chat
before its first read, so an existing conversation does not flash the new-chat
empty state. Work-session headings keep their own title.

In local agent chat, `/help <feedback>` files a user-authored issue in

and selected session ID, server startup revision and UI build revision are published; no transcript, log or credential is

separate IDs; existing general instances and their transcript references remain.

one definition; its `created` is the instance in the creator's project. This is
operational metadata, not a second conversation record.

### Managed review and publication evidence

New local issue families pin `candidate-evidence-v1` and `pre-action-proof-v2`.
`POST /api/agents/work/:id/validation` (CLI `agent work-validation`) appends an
idempotent, writer-authenticated report for a clean committed base/head. The
small record keeps command outcomes/log references and per-issue pre-action proof;
execution is writer-reported, never server-attested. Failed or missing execution
blocks review before reserving a round and blocks publication. Rounds snapshot
their submitted report; later same-candidate evidence cannot erase declared
commands or turn a known failed check into a compiler exclusion. Publication
also checks the latest report. Compiler exclusions require repo-specific evidence.
See `docs/agents.md` for the contract. No existing work/config/round is migrated;
source review, execution reports, publication and final readiness remain distinct.

`src/core/agents/reviews.ts` is the single independent-review engine for local
work families and shared repository writers. It uses existing Fleet sessions and
provider transcripts, storing only identities, exact candidates and verdicts.
`shared-reviews.ts` binds it to the current cloud writer and the work item's
cumulative journal. Prepare/review/collect/retry-review run routes require that
writer's session capability. Completed verdicts cannot be replaced or the
three-round budget reset by changing runs, agents or execution installations.

Reviewer reservations are local, bound to an immutable work ID and checkout.
Foreign cloud IDs are metadata, never local session-read or stop authority.
Host handoff replaces only incomplete read-only reviewers with freshly reserved
local IDs while preserving the candidate and round. Shared publication receipts
on existing immutable actions map the reviewed tree to the App-authored commit;
current policy, accountability and consent are rechecked at dispatch. Cloud
migration/setup remains required; missing evidence fails closed.

Sessions lists and their attention badge contain user sessions only. The server
annotates sessions with `agentOwner` from persisted local conversation/work and
shared run/reviewer links, following recorded parent links for descendants.
This is navigation metadata, not authorization. Closed-list pagination uses
`GET /api/sessions/closed?human=1` so counts and reopen-last also exclude agent
work. Fleet/CLI state, transcript access and direct operational links remain
available. A selected project tab suppresses the redundant repository heading
and saved repository collapse state in its Sessions rail.

### Closing an agent's completed work

Local agent coordinators can close completed work with `agentbox agent session
<agent> <session> close --request <UUID> --activity <lastActivityAt> --reason
<evidence>`. `POST /api/agents/local/:id/sessions/:session` accepts the same
`{request,action,activity,reason}`; action is `close` or `restore`. A session
capability must be the recorded current coordinator or work owner; invalid
capabilities and unrelated/historical sessions are refused. The existing
loopback operator UI may use the same operation. No publication authority is
added. The main chat stays available and cannot be closed by this operation.

The Fleet serializes these operations with sends. Closing checks the inspected
activity is unchanged, the session is idle, no child session remains open,
no PR claim/wait/decision is pending, and the transcript/account/resume cwd
are available. Only that worker is closed; its transcript/worktree and cache
clock remain. Request IDs journal the attempt; uncertain attempts are never
replayed automatically. Agent judgement is required: idle alone is not done.

The daily sweep (`src/core/agents/sweep.ts`, issue #39) is the exception the
user asked for: each day at `agentSweepAt` ("HH:MM" on this machine's clock,
default 23:00; empty turns it off), every local agent's work sessions idle
for two hours are closed whether or not they look done. It uses the same
serialized `closeIfIdle`, with what each session started closed with it. It
never touches a main chat (current or earlier), a session no agent owns, or a
shared agent's runs. It keeps, and gives the reason for, a session with an
armed wait, an open, snoozed or undelivered Review card, an open PR it
claimed, or a child that is running or active in the last two hours. Each
sweep's closed and kept sessions are in the agent's Feed (`GET
/api/agents/local/:id/sweeps`, the last 14). A sweep missed by more than four
hours, because the server was down, is not made up.

Closed work is collapsed by default beneath Show closed sessions and does
not inflate the active work count. Its transcript remains readable. Restore
cached session reuses the exact provider conversation and pinned account,
checks actual `Session.cacheWarmUntil` inside the Fleet lock, and refuses
expired/revoked work authority or replaced conversations. It sends no new
prompt. Cold history remains readable, without claiming its cache survived.
